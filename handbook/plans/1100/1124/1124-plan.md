## What the issue asked, and what the measurement found

The issue (a body, no comments) files H15d's restore and offers one lead, marked unproven: `handbook/specs/settle-doctrine.md` clause 13, a tolerance sized to the drift constants, on the guess that the 900 ms window crosses the idle delay. **The lead does not hold for H15d, on three readings:**

1. **The flight re-arms the idle timer at the click.** The click handler in `bindStations` (`src/site/home/cards.ts`) calls `on.fly`, which `src/site/home/app.ts` binds to `flyTo`; `flyTo` calls `stopDrift`, which kills the drift tween, clears `idleTimer` and calls `armDrift`, which sets a fresh `setTimeout(..., IDLE_DELAY_MS)` (9000 ms). The probe's wrap of `window.setTimeout` logged exactly one 9000 ms timer, armed 0.0 to 1.2 ms after the click, on every flight it made (`out/1124-dry-run/1124-probe2.log`, each line's `timers` field).
2. **H15d's whole step took under 2.4 s on every failing job**, click to second read, so the window closed about 6.6 s before the drift could start. Each job's own log (`gh api --allow-escape-sequences repos/ahl-gram/Vellum/actions/jobs/<job>/logs`), from the H15c PASS line to the H15d FAIL line: job 121950518823 01:19:24.804 to 01:19:27.148 (2.34 s); job 123815433838 00:26:15.456 to 00:26:17.813 (2.36 s); job 123993721471 09:41:59.311 to 09:42:01.684 (2.37 s).
3. **What moved is the flight's own last hundredth of a pixel.** In all three payloads only x moves (+0.01); y sits on the clamp (y = -1157.931 x s / 2, which is -1159.6 at s 2.00288) and the scale does not change, because `stationFlightView` keeps `max(cam.s, fit * 2.6)` and the drift had left the scale at 2.0028, above `fit * 2.6` = 1.6526. The flight's tail moves x alone; a resumed drift would move the scale (`DRIFT_SCALE`) and the clamped y with it.

**The cause.** A transform reads to six significant digits, through `getComputedStyle` and through the inline `style.transform` alike (probe 1 read both side by side: `translate(-1148.55px, -1159.57px) scale(2.00282)` and `matrix(2.00282, 0, 0, 2.00282, -1148.55, -1159.57)`), which at x near -1148 is 0.01 px. The 1.5 s `power3.inOut` flight writes the camera on every frame until about 1490 ms after the click (probe 2: last write at +1482.5 to +1496.8 ms over 25 flights), but its printed matrix often stops changing well before that (probe 1, 36 flights: last printed change at +1368.4 to +1478.0 ms). Today's wait (`makeStable` on `{ open, xform }`, two equal reads about 51 ms apart) can therefore hand over before the flight has landed, and when the flight's last printed step lands after the hand-over, the 900 ms window reads it as a 0.01 px move. The wait came in with PR #1079 (2026-10-26), which replaced a blind `sleep(2200)` that always outlasted the flight; the first H15d row is dated 2026-10-27.

**Reproduced on the Mac**, local harness browser (Brave), by probe 1 (`out/1124-dry-run/1124-probe.ts`, log `out/1124-dry-run/1124-probe.log`, run as `node out/1124-dry-run/1124-probe.ts` on the site `npm run build` made in the planner's tree at `108f8db6`): 36 station flights from a varied start (a small wheel and a 26 px drag before each), read every 50 ms and judged by today's predicate. ## The design

H15d keeps its claim, its sentence, its two stillness reads of the computed transform and their exact comparison. Only the wait before them changes. It stops comparing printed matrices and hands over on the first read, with the Reading Room slip open (the departure, as today), at which **no write to the sheet's `style` has landed since the previous read, and at least one animation frame has run between the two reads**. One payload, evaluated just before the click, installs both counters in the page: a `requestAnimationFrame` loop counting frames, and a `MutationObserver` on `#lf-sheet`'s `style` attribute counting the records the camera's `apply` writes. The flight writes on every frame through its last one, and the observer counts every write that changes the declared value, below the printed precision too (probe 2's `unchangedText`: 10 to 13 records per flight leave the attribute's text unchanged), so "a frame with no write" is the flight having landed, at any precision. A write of an identical value is not counted: probe 3's first creep staging, which set the sheet's transform each frame to the value it already printed, recorded no write after its first and H15d passed (its H15d line read `"landing":{"open":true,"writes":180,"frame":96}`, flight1 and flight2 both `matrix(2.00285, 0, 0, 2.00285, -1148.57, -1159.58)`; the second creep run, which moves the sheet, overwrote that log, so this line is its record).

**Alternatives rejected:**

- **A tolerance sized to the drift (the issue's lead).** The drift cannot run inside this window (above), so the tolerance would be sized to a cause that is absent, and it would pass a flight that had not landed: clause 1, the defect is the statistic, not the threshold.
- **A tolerance of one printed step (0.01 px), or one sized to the flight's tail.** The tail's size follows the flight's distance, which follows the history before H15d, and the wait would still hand over mid-flight, which is the actual defect.
- **The inline `style.transform` as a full-precision read.** It prints to the same six significant digits (probe 1).
- **The `attributeStyleMap` value as the read.** It reads a single-precision value (probe 2's `typedAtHandover`, for example `1.9996349811553955`, which `Math.fround` leaves unchanged), still needs the frame witness, and asks "did the number change" where the write count asks "did the page write", which is the question.
- **The write count without the frame counter.** Two reads with no frame between them see no write either, so a stalled runner would hand over mid-flight. The Mac never showed such a pair (0 in 36 flights, CPU throttled up to 10x), so this half guards the runner the Mac cannot stage.
- **A wait of `STATION_FLIGHT_SECONDS` on the page's clock.** gsap's lag smoothing stretches a tween past its nominal duration on a stalled runner (a gap over 500 ms counts as 33: `_lagThreshold = 500` and `_adjustedLag = 33` in the installed `gsap/dist/gsap.js`), and a sleep sized to an animation is a bet (`handbook/specs/settle-doctrine.md`, the environment bullet opening "A sleep past an animation's nominal duration").
- **A marker set by the flight's `onComplete` in `src/site/home/app.ts`.** It changes product code for a test's sake, and the harness can read what it needs.
- **Lifting `COUNT_FRAMES` from `e2e/suites/cards/cap.ts` into `e2e/support/`** (call C3).
- **Comparing the stillness reads at full precision too** (call C9).
