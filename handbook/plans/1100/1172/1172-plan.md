## The design

**The test server holds home's bundle for H13e, and H13e reads the window the hold keeps open.** No network throttle. `e2e/site-server.ts`, which serves the built site in the lane's own process, gains a gate: while `serverState.heldBundle` is a promise, a request for `/app.bundle.js` (home's bundle, `scripts/build-app-bundles.ts`) waits on it before it is served, and every other file is served as before. A new exported `withHeldBundle(body)` in the same file sets the hold, hands the body a `release` function, and lets the bundle go in a `finally`, after a body that passed or threw, so a failed H13e never leaves later checks loading a home whose bundle never arrives (the leak class Issue #1178 closed for the throttle).

`h13ePrmNoFlash` (`e2e/suites/home/doors.ts`) then:

1. marks the H13d page (`window.__h13d = 1`, as today);
2. inside `withHeldBundle`, navigates to `about:blank` and then home, and waits with `makeSettle` (tolerant, since the reads cross a navigation) for the first read of the fresh page: `!old && ready`;
3. keeps sampling every 75 ms until a sample's page clock (`performance.now()`) reads 2000 ms or more (`HELD_MS`), the bundle held all the while, so `.cam` cannot appear: each sample reads `t`, `old`, `ready`, `door` (`doorShown` in `e2e/suites/home/reads.ts`), `cam`, and the explorer card's computed reveal statement `[animationName, animationDuration, animationDelay, animationFillMode]`;
4. lets the bundle go and samples until `.cam` appears (a readiness wait that throws with its last read), then four samples more;
5. checks, all at once: `.cam` appeared; no sample, held or after, read a door; every held sample read no `.cam` (the witness that the window was held open); and every held sample read the reveal statement `lf-doors-reveal 0s 10s forwards`, the one H13g pins without reduced motion (C6).

The window is now two seconds of the page's own clock on any runner and any page weight, and the step costs about 2.5 s on the Mac where it cost about 9.4 s. The issue's "event-driven wait for the bundle" is step 4, and its "different throttle that does not depend on the runner's pace" is the hold.

**What the check holds, counted** (settle-doctrine, "What a step holds"): two claims, both held nowhere else, on one page (home), so the step is thin. (1) Under reduced motion, on a healthy load whose bundle comes late, no door shows before the bundle boots, nor in the four samples after: held by no other check (M1 above reds H13e alone; H13d passes). (2) Under reduced motion the reveal is still the 10 s timer before the boot: H13g pins the same statement without reduced motion and passes under M1, and `test/site/landfall-doors.test.ts` reads the unreduced statement. The step's seconds are read from the pull request's own CI run (Evidence).

### Alternatives rejected, with the reason

- **Keep the throttle and let the sampler run until `.cam` on the page's clock** (Q1 option 2, not taken: Rulings): the boot stays at about 9.2 s on the Mac, 2.2 s before the doors' own 10 s reveal; with one more prefetched file of 150000 bytes or more the growth probe read the reveal first and a door on screen for about 0.7 s before the boot, so the check would red as a flash that is the designed fallback, and the step keeps costing about 9.5 s.
- **A lighter throttle** (Q1 option 3, not taken: Rulings): the window still moves with every file the page downloads (360000 B/s read 3081 ms, 600000 B/s read 1354 ms), so the same edge returns as the page changes.
- **Leave H13e out of the run and close the issue** (Q1 option 4, not taken: Rulings): nothing else holds the claim; with the reduced-motion delay zeroed, H13d still passes (What is measured).
- **Ten lane C passes in a row, one re-run after another, as the issue's fix text proposes** (Q2 option 2, not taken: Rulings): about 100 minutes of one runner, and a streak of passes cannot tell the fix from luck, since the old design passed 230 in a row before its first red; the margins the new check prints can.
- **Ten at once, by nine whole CI runs started together** (Q2 option 3, not taken: Rulings): about 15 minutes, but 63 jobs crowd every other pull request's checks, and it reads the same streak, not the margins.
- **Hold the bundle through CDP `Fetch` interception**: `onCdpMessage` in `e2e/harness.ts` routes no CDP event to a suite, so the check would need a second socket to the page target and an event loop of its own; the server already runs in the lane's process and already carries one switch (`blockWorker`).
- **Hold it in the runner or the harness rather than the server**: the hold belongs to one check, not to every suite, and the runner's hooks in `e2e/support/runner.ts` are the rescue every suite shares (settle-doctrine clause 14), not a place for one check's fixture.
- **`withHeldBundle(state, body)` writing through a state passed in**: `no-param-reassign` with `props: true` (`eslint.config.ts`) refuses a write through a parameter; the server module writes its own `serverState` (C4).
- **Capture the old sampler's per-sample log on a CI red first, as the issue's fix text proposes**: the 237 timestamps and the probe's per-sample log already place the boot at the sampler's edge, a capture would need H13e back in the run on the old design to red again, and the new check prints its window (held samples, release and `.cam` times) on every run, pass or fail (C10).
- **Read only the computed reveal statement and drop the sampler**: deterministic and it reds M1, but it cannot see a door that shows by any route other than the delay; Gate 1 item 21 keeps the sampler beside it (C6).
