## The design

**The order, for every red job on a lane's pull request** (rulings 1, 2, 4, 5, 7, 8, 10, 11 and 12):

1. The orchestrator reads the failing job's log by job id, `gh api --allow-escape-sequences repos/ahl-gram/Vellum/actions/jobs/<job>/logs` (the form settle-doctrine's launch-retry bullet already uses; a job id names one attempt of one job). `gh pr checks <PR>` prints each job's URL ending in its id, but only for each job's latest attempt (after AT1's re-run it prints lane C as 121032294674, attempt 2; attempt 1's was 121030451946), so the orchestrator passes the first read's job id to the lane. It reads the numbers on the `FAIL` lines and, for an e2e lane, the fingerprint its verdict line ends on (`LANE C FAILED (...)  on linux ...; "Chart № 42" 98.02px; № in Liberation Serif; select 29.22px` in AT1's attempt 1), against the subsection "Where the Mac and the CI runner disagree".
2. **A red of the same check on several lanes' pull requests at once** (a runner image moving under every lane, say) is read and fixed once, by the lane the orchestrator picks, the others merging `main` after its pull request lands; their local runs go one at a time (Gate 2 item 11; settle-doctrine's "The preflight is not a lock").
3. It sends the lane on with the red, its job id and what it read. The lane finds what failed: a check's suite by `git grep -n -P '"[^"]*\b<check id>\b' -- e2e/suites` (the suite is the hit's first path segment under `e2e/suites/`, `.ts` dropped, the rule `p1049-find-suite.ts` runs: for `e2e/suites/print-room/fallback.ts`, which holds PR6, the suite is `print-room`, not `fallback`; the plan skeptic's sweep found 431 of the 438 ids in step and check labels naming one suite this way, and for the other 7, H1, H2, H6, H8, D1, D3 and EA4, the failing lane's `suites on port` line, then the `FAIL` line's text, settles it), a unit test file from the log, or, for a red with no failing check, the step the log names. It takes the Mac's reading at that commit (an e2e suite after `npm run build`, as `VELLUM_E2E_SUITES=<suite> npm run test:e2e`; a unit test file as `npm test -- <file>`, which loads the source-read guard CI loads; a step as its own `npm run check`, `npm run lint` or `npm run format:check`), unless it already has a green run there, saying for a suite which suites ran before it in the CI lane, since a suite can red in lane order and pass alone (clause 14). For an e2e check whose `FAIL` line does not report a wait or a budget run out (a line holding `timeout`, `timed out` or `budget`), it takes the staged reading too (the same run with `VELLUM_E2E_RUNNER_LAYOUT=1`), quoting its `RUNNER LAYOUT:` line and comparing its fingerprint sizes with the failing job's; a timeout is never explained (step 5), so a staged run could change nothing for it. A launch failure, a job's time cap or a hang has no Mac reading. It reads the log against the subsection itself, and reports.
4. A red the Mac run reproduces, or one the read puts down to the builder's own code, is no CI-only red: the builder's definition already decides it. It is not re-run (Gate 2 item 10: a red is yours until proven a flake, and this one is proven not to be).
5. **Explained** (rulings 1, 4, 12), stated once, in settle-doctrine's flake sequence, step 1, which every session is sent to (ruling 5): a red on CI is explained where an entry of the subsection names the difference and the numbers are the ones its home gives, a staged run that reds as CI did included; a wait or a budget that ran out, and a red with no failing check (a launch failure, a job's time cap, a hang), never are, since the runner's speed differs from run to run (they take step 7's re-run). An explained red gets no flake row and no re-run. The orchestrator rules it and tells the lane, and the lane then:
   - where the explaining entry's home is a rule for the code under test and not for the check (the Media queries entry's affordance gate, whose home is `handbook/specs/cascade-traps.md`; the File names entry's path case), treats the red as a defect in the code: its own to fix where its own code caused it, a hand-back where the plan's design did;
   - otherwise rewrites the check as the entry's home says (for a layout difference, reading the number off the room's own layout in the run or asserting it with its margin measured on both browsers' layouts), or in the form of the check the home names where the home is a check (the Taps entry's `p30Tablet`);
   - leaves above the rewritten check the one line `// <date>: rewritten for a red on CI, run <run id>: <why>`, a fixed token no line in the repo carries today (`git grep -n -F "rewritten for a red on CI"` printed nothing at b6f536a4), so the older provenance lines naming a CI run (RR42's in `e2e/suites/reading-room/gestures.ts`, among others) are never read as the marker;
   - runs a rewritten layout check's suite with `VELLUM_E2E_RUNNER_LAYOUT=1` before the push, its `RUNNER LAYOUT:` line quoted (Issue #1047's switch exists for that run);
   - names each rewritten check, and how, in a new dated comment on the issue (workflow step 12: the comment made before the pull request opened is never edited, and CI first runs once the pull request is open, so every rewrite comes after it), and proves it bites, as its build section already requires of a guard changed after the prover's round.

   A rewrite made after the cold review's one round is read by the orchestrator before the merge, its report to Alex naming each rewritten check (ruling 7).
6. **Not rewritten, pulled out** (ruling 8): a check whose rewrite reds again on CI, and a check that already carries the marker, from any lane's pull request; the marker is permanent, so a check rewritten once is pulled out at its next explained red, whatever moved. The builder first gives each later check in its suite that reads a state the step holding it sets or waits for its own wait for that state (item 11's precondition, from Issue #873) and commits, then reports what it read and tried, naming the suite, the step and every check that step holds (an `E2E_SKIPS` entry names a step, so all of them leave the run together, as `{ suite: "chart-drawer", step: "CD25, CD26, CD30", issue: 716 }` does). The orchestrator files an issue recording what the lane read and tried, puts it on the board, takes the lane's tree out loud ("One writer per tree"), and adds the one entry in `E2E_SKIPS` (`e2e/support/skips.ts`) naming the suite, the step and the issue, as item 11 says ("Whoever files the issue pulls the check out"; "a lane whose plan does not name `e2e/support/skips.ts` never edits it"); it runs the suite there before it pushes and says so in the pull request's body. The entry has to ride in the pull request whose CI it clears, since a skip whose suite ran without meeting its step is reported (`unmetSkips` in `e2e/support/skips.ts`) and the step may exist only on the lane's branch. The pull request then merges without the check, and the lane's build ends there; its tree is retired after the merge ("Handing over and retiring a lane"). A unit test has no skip list to leave, so one whose rewrite reds again is handed back to a planner (ruling 10).
7. **Not explained**: re-run once on Gate 2 item 10's terms, in ruling 11's order: the orchestrator opens a pull request of its own adding the row to `.claude/skills/vellum-footguns/references/flake-record.md`, posts item 10's pull request comment on the lane's pull request, then re-runs that job alone, `gh run rerun <run> --job <job>` (not `--failed`, which re-runs every failed job, an explained one beside it included), its own pull request's checks running beside the re-run, and sets the row's disposition from the re-run in its pull request, one more for Alex to merge. Gate 2 item 10's "alone, never two PRs concurrently" is read as never re-running two pull requests' reds at once, which this keeps; the row pull request's checks run on machines of their own, so they cannot change the re-run's result, and at most queue it. Three cases more:
   - **A run that holds an explained red as well**: the lane's push of its rewrite is the re-run, made once the row's pull request is open, since `.github/workflows/ci.yml` puts every run of a pull request in one `concurrency` group with `cancel-in-progress` on, so a push would cancel a re-run still in progress. How GitHub treats a re-run attempt inside that group is UNVERIFIABLE here (no re-run was started); taking the push as the re-run makes the question moot.
   - **A row that is its step's third** (clause 12): its pull request also carries clause 12's issue and skip, no re-run is made, and the lane merges `main` once it lands.
   - **Two row pull requests** append to the record's end and conflict on the second merge, so they merge as two errata rows do ("Merging"). Each row pull request runs every job twice (`.github/workflows/ci.yml` filters no path): once for the row, once for its disposition.
8. The re-run clears the red only if that check passes: a flake, and the lane goes on with its build. A red in another check on the re-run is a new red, read the same way. A re-run that reds the same check again is read the same way and handed back, saying whether its numbers are the first run's (Issue #1034's lesson below), and it reaches a fresh planner with its read, never as the bare red; a timeout that reds again goes the same way (ruling 12). A difference the subsection does not name is never "explained", so it reaches a planner this way, named so; its line joins the subsection in the change that records it, as the subsection's own opening says.

**What the rulings cost, in one line** (rulings 1, 7 and 8, as ruling 12 leaves them): a rewrite, and the later checks' waits a pull-out needs, made after the cold review are read by nobody but the orchestrator before the merge; a check pulled out is unguarded until its issue is fixed; and a check rewritten once is pulled out at its next explained red, whatever moved. Timeouts keep the flake route (a row and one re-run) and so stay counted in the record.

**Why ruling 12 re-took the timeout** (the measurement put to Alex, `node p1049-timeout-tally.ts`, scratchpad): 40 of the flake record's 124 rows carry a timeout or a budget run out in their payload; the 33 whose cause was found (CD57) were an aim in the check, settled by PR #861, not the runner's speed; the CD25, CD26, CD30 family's 5 were a press that never registered, cause not proven (Issue #716); the other 2 are open as "a slow runner, not investigated". None was shown to be the runner's speed.

**What the read costs**, before the fix or the re-run: one log read by the orchestrator; a build and up to two local runs of one suite by the lane (the suites Issue #1034's lane ran locally took 14.1 s, `specimen`, to 226.6 s, `stage`, each, its comment 6378023819); one wake-up of the lane; and, for an unexplained red, one failed-job re-run (AT1's lane C re-run took 6m35s, against 8m36s for all seven jobs of its first attempt) and one row pull request, with its own CI run twice over (PR #1056's seven jobs ran 00:57:09 to 01:05:37), for Alex to merge.

**Alternatives rejected:**

- **The issue's `gh run view <run> --job <job> --log`.** After a re-run of the failed job it returns the newest attempt's log: on AT1's run, `gh run view 40147029775 --job 121030451946 --log` printed no `FAIL  AT1` line and the per-job API form printed one.
- **`gh run rerun <run> --failed`.** It re-runs every failed job (`gh run rerun --help`: "Rerun only failed jobs"), an explained red's job beside the unexplained one included; `--job <job>` re-runs the one.
- **`git grep -n -F '"<check id>"'`.** It finds a check only where a step is named for it alone; it found nothing for SW4, CD25, CD26, CD30, CD7b, HG2 and BR8.
- **"The hit's file name, or its folder's, is the suite".** Five nested files share a suite's name (`print-room/fallback.ts`, `reading-room/fallback.ts`, `survey/turn.ts`, `chart-drawer/prospect.ts`, `stage/stage.ts`), so the file name runs the wrong suite; the first path segment is the rule.

- **Treating a timeout as explained by the runner's speed, and doubling its limit.** Ruled out by ruling 12.
