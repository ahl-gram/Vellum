## The design

**The rule's purpose is its first clause.** The archive holds every plan a build was made to. A revision is a plan finished again by a fresh `vellum-planner` after the plan came back to it: a builder's hand-back, or a finding about the plan's design at step 14 or 15. It is a new file beside the plan it revises, never written over it, named `<N>-r<k>-plan.md` (`<N>-<label>-r<k>-plan.md` for a later pull request), and it is committed with the first commit its builder makes, copied unchanged as it stood after its rulings were folded in.

**The name is chosen once, by the planner, and carried.** The revising planner writes the revision to the scratchpad under the name it will be archived at. The dispatcher archives it to `out/plans/` and the issue under that name. The implementer copies it into `handbook/plans/<N>/` under that name. Nobody renames a plan on the way.

**Workflow step 8 is the one home of that name** (revision 1, the cold review's finding 3). Step 8 states the name forms, what `k` counts and when a revision takes the plain name instead. `.claude/agents/vellum-planner.md` points at step 8 for the rule and holds only what step 8 does not: the commands that read the three places the rule reads, and what to write over or beside in the scratchpad. `.claude/agents/vellum-implementer.md` and `handbook/specs/orchestration.md` already point at step 8 and carry no copy.

**`k` counts revisions per pull request and is never used twice** (D2, ruled A): one more than the highest revision of that pull request's plan on its pushed branch, on main or in the opening line of a `Plan archive, not a ruling:` comment on the issue, the plan the pull request first committed counting as 0. Counting the issue's archive as well as the branch keeps a second hand-back from reusing a number whose file the first revision's builder has not committed yet. A revision copied into the archive after its pull request merged keeps the number its own text gives it (`1034-r3`, `1034-r4`, `873-r2`). Precedent on main: `778-pr2-r1-plan.md` to `778-pr2-r4-plan.md`, numbered within Issue #778's second pull request, and `751-loupe-r1-plan.md`, numbered within Issue #751's second, beside the first pull request's `751-r1-plan.md` and `751-r2-plan.md`.

**The branch the rule reads is the one the implementer's report names, read by command** (revision 1, the cold review's finding 2). An implementer's report names the branch its tree stands on and the head `git ls-remote origin refs/heads/<branch>` prints for it, or says it prints nothing. The dispatcher hands that report to the fresh planner as the hand-back (`handbook/specs/orchestration.md`), and the planner reads the branch's state itself: `git ls-remote` for its head, then `git fetch` and `git ls-tree` for the plans it carries. The plan a pull request first commits goes in the branch's first commit, which the implementer pushes as soon as it makes it (its definition: "Commit and push at the first commit"), so a branch `git ls-remote` does not find, or whose pushed head carries no plan of the pull request, has no plan of the pull request committed on it, and a revision the planner gives the plain name is never one the implementer's branch already carries. A revision whose file is committed but not yet pushed is still counted, from the issue's archive. The report names the tree's branch, never whether a commit was made: a fresh implementer that takes over a pull request's branch and hands back before it commits has made no commit on a branch that already carries the plan. A report that names no branch stops the planner before it writes the revision.

**Every revision a build was made to is committed** (D1, ruled A), each with its builder's first commit: no lane knows at that moment whether a later hand-back will supersede it.

**A revision finished before the pushed branch carries any plan of its pull request** (D3, ruled A) is the plan that pull request's build first commits: the planner gives it the name of the plan it supersedes and writes it over that scratchpad file, which the dispatcher has already archived in two places. Precedent: Issue #1047, whose `handbook/plans/1047/1047-plan.md` is byte for byte the dispatcher's `1047-plan-r1-20261024T235103Z.md`. Two archive comments then name one file, and the sha256 on their opening lines says which is which.

**Only the plan file is archived** (D5, ruled B). A file a plan names as standing beside it stays where the dispatcher archived it; the committed `handbook/plans/751/751-r2-plan.md`'s "`751-r2-fmt/rules.css` beside it is not archived" stands.

**A change at review that no planner revised stays in the PR body**, named there with the difference.

**The backfill applies the same test to the merged pull requests** (D4, ruled A): the revision each was built to goes in the repo beside its frozen original, copied byte for byte from the dispatcher's `out/plans/` copy, except Issue #873's revision 2, which no file holds and which is rebuilt from the transcripts of the session that wrote it (section 10, Alex's comment 6397392339).

**A reconstructed plan is the plan unchanged, and its provenance lives beside it, not in it** (call 10). `handbook/plans/873/873-r2-plan.md` holds exactly the text its builder read, so its sha256 is the check. The note that it is reconstructed and not a byte-for-byte copy goes in the commit that adds it, in the `handbook/errata/prose.md` row (section 11), in the pull request body and in this plan.

### Alternatives rejected

- **Renaming at copy time** (the planner writes `N-plan-r1.md`, the implementer commits `N-r1-plan.md`, as Issues #1043, #1045 and #1047 did): every rename is a judgment the cheaper implementer has to make and a mismatch between the issue's archive comment and the committed file.
- **The issue body's suggested parenthetical, word for word**, "a plan that changes at review (a skeptic's finding folded before the pull request is reviewed, not a hand-back)": its meaning is kept and its words are not, since "not a hand-back" would define a revision a second time (call 2).
- **A repo test that every file under `handbook/plans/` matches the naming forms**: Alex chose the PR #721 row in `handbook/errata/guards.md` over such a test on 2026-09-29.
- **Counting `k` from the branch alone**: a second hand-back reuses the number of a revision archived on the issue but not yet committed.
- **Renumbering backfilled files 1, 2 in order of hand-back**: Alex ruled D2 A.
- **Archiving the files a plan names as standing beside it**: Alex ruled D5 B.
- **The planner finds the branch for itself**, by `git ls-remote origin` over `*/<N>-*` or by the issue's linked pull request: an issue that ships as several pull requests has several such branches, and a hand-back before the pull request opens, the common case, has no linked pull request, so the planner would be guessing which branch is the build's.
- **The dispatcher's brief carries the branch**, read from the lane's tree: one more hop that can drop it, when the implementer, which already writes the report the dispatcher forwards, knows the branch exactly.
- **The implementer pushes every commit before it reports** (this revision's first draft): each push of a hand-back's WIP commit on an open pull request runs the whole of CI (`.github/workflows/ci.yml` runs on `pull_request`), a cost in every lane, and the rule needs no more than the first commit, which the implementer already pushes as soon as it makes it, and the issue's archive (the plan skeptic's finding 5).
- **The report says that no commit was made, in place of the branch** (this revision's first draft): a fresh implementer that takes over a pull request's branch and hands back before it commits made no commit, on a branch that carries the plan, and a planner reading "no commit" would give the revision the plain name the branch already holds (the plan skeptic's finding 2).
- **The branch requirement in the hand-back paragraph** ("The hand-back names the plan line ..."): PR #1059 rewrites that paragraph, so the two pull requests would conflict there; "When to stop" is the report's own list and PR #1059 does not touch it (call 14).
- **The planner's definition as the home of the naming rule**: step 8 already holds the archive's other names (`<N>-plan.md`, `<N>-<label>-plan.md`) and is what the implementer and orchestration cite; splitting a revision's name from them puts one naming scheme in two places (call 13).
- **A provenance header inside `873-r2-plan.md`**: the file would then equal nothing its builder read, so its fidelity could no longer be checked by sha256, and step 8 copies a plan "exactly" and never edits it afterwards (call 10).
- **A side file carrying the provenance** (`873-r2-provenance.md`): a second home for what the errata row and commit 8 already say, and the one file in `handbook/plans/` that is not a plan.
