## The design

### The instrument: a browser check

The witness is a **browser check**, H5c, in the hunt suite. It is neither a unit test nor a lint or type rule.

- **What the check claims.** H5b states it: the solved reveal on the page names what the place was once called. Two rules make this a browser check:
  - "What a page shows" is a browser check's to hold (`handbook/specs/check-placement.md`, the unit suite's bullet against searching source text).
  - A ratified acceptance gets a driving check beside any pure-function read (`vellum-footguns` Gate 1 item 20). The acceptance is Issue #49's ruling 7, which is the reveal. The pure-function reads are `test/render/former-name-reach.test.ts`, which tests `revealLore` and `revealFormerLine`.
- **What a browser check holds that nothing else does.** The planner's dry run staged two mutations in the built bundle, and both red H5c:
  - **m1: the page's DOM append is dropped** in `renderReveal` (`src/site/seed-of-the-day/reveal.ts`).
  - **m2: the page's wiring drops the name.** In `showReveal` (`src/site/seed-of-the-day/app-hunt.ts`), the page passes a `Reveal` without `formerName`.

  No unit test can see m2: the unit tests call `revealLore` and `revealFormerLine` directly, never through the page.

**Rejected: a unit test of `renderReveal` over `test-support/element-shim.ts`.** The shim has `append`, `replaceChildren` and `textContent`, so such a test would work and would red on m1. It would not red on m2, and it holds nothing H5c does not. Adding it gives m1 a second holder and gives no claim a first one.

**Rejected: a lint or type rule.** Neither can see what the page does at run time. Making `Reveal.formerName` a required `string | null` would force anyone building a `Reveal` by hand to state the field. It would not show that the field reaches the reveal.

**Rejected: moving `HUNT_DAY` to 2026-11-03**, so that H5b takes its naming arm with no new step. That would cost the "says nothing" arm its witness, the gap this issue closes, only reversed. It would also re-fixture every hunt check (H3 to H12, HD, HG) on a day no browser has read.

**Rejected: restoring a solved day from the store instead of solving live.** The page restores a solve from `vellum.hunt.v1` on reload. Using that would save only the click, which costs milliseconds. It would still need the in-page quarry read for the expected name, and it would tie the check to the store's shape. The issue asks for a solve "the way H4 does".

### The day: 2026-10-05

The step uses a constant of its own, `FORMER_DAY = Date.UTC(2026, 9, 5, 12)`, the date of `FIXED_DAY`.

- **Why 2026-10-05.** The quarry on that day has been read in a browser four times, each including the legend exclusion that only the page computes. It read Zodo, once Tho, every time:
  - CI run 37379661660, job 111998053304: H5b's payload `{"formerName":"Tho","text":"Zodo, founded in the year 506.Once called Tho...."}`;
  - the planner's dry run at 36c39c2d, on this machine's layout;
  - the same run with the CI runner's layout staged;
  - PR #1131's head, 4062ee18.
- **Why not 2026-11-03.** It is the first day in recon's 60-day sweep that gives H11, H12 and a former name together. H5c does not run H11 or H12, so that day buys nothing, and no browser has read it.
- **Why its own constant and not `FIXED_DAY`.** Alex ruled `FIXED_DAY` for the whole run (PR #784). It may move for a reason that has nothing to do with this check, and this witness should not move with it. The constant mirrors `HUNT_DAY`.

### Where the step runs

`run` in `e2e/suites/hunt.ts` gets a second `onDay`, run after the first one returns, never nested inside it:

```ts
await onDay(ctx, FORMER_DAY, () => step("H5c", () => h5cFormerName(huntKit(ctx))));
```

- **Why after the first `onDay`.** `h11Labels` and `h12Terrain` read the document the hunt day left.
- **Why not nested.** Nesting would put two override clocks on one document, and which one wins depends on script order, which has not been measured.
- **What the next suite inherits.** The step ends settled on `/seed-of-the-day/`, the 2026-10-05 page solved. `NEEDS_PREDECESSOR`'s `"print-room": "hunt"` still holds (`e2e/support/suites.ts`): print-room needs a page that is not the Explorer, and this is one. print-room's first navigate leaves for `/explorer/`, which is a new document on the harness's clock.

### The step's file, and the quarry read

- **The step's file.** The step lives in a new part file, `e2e/suites/hunt/former.ts`. A suite's parts belong in the folder beside its entry (`handbook/specs/site-architecture.md`).
- **The quarry read.** It needs the in-page quarry read, `huntQuarry`. That function now lives inside `hunt.ts` and reads the module constant `HUNT_SEED`. It moves verbatim to a new `e2e/suites/hunt/quarry.ts`, taking `seed` as a parameter, and both `hunt.ts` and `former.ts` import it from there.
- **Why move it.** If `former.ts` imported a value from `hunt.ts`, which imports `former.ts`, the two modules would import each other at load time. The parts that exist today import only types from `hunt.ts`. The move also brings `hunt.ts` down from 348 lines to about 310.

### The id: H5c

The step and its check are named H5c, not H5b.

- `skipFor` in `e2e/support/skips.ts` matches a skip entry by step name alone, whatever its suite.
- `e2e/suites/home/frame.ts` already has a check H5b.
- `git grep -n -E '"H5c|step\("H5c' -- e2e` finds nothing.

H5b stays exactly as it is. It still witnesses the arm its day takes: "says nothing" on 2026-10-07.

### The wait

The step navigates through `about:blank` and then to `/seed-of-the-day/`. Clause 9 is why: the current page is already that URL, and a same-URL navigate would return on the stale, solved document of the hunt day.

The step then waits with `makeSettle({ tolerant: true })` until all of these hold:

- the chart's `data-vellum-seed` equals 20261005, a token only the new document sets;
- the clue list is non-empty, which shows `setupHunt` ran;
- the hunt card is shown;
- the map is not `.solved`.

The wait does not ask for at least 3 clues, since that is H1's claim (clause 6). The read is a readiness wait, so it throws when it runs out of tries (clause 4). It sits inside `step`, where `vellum/e2e-throw-inside-step` looks for it: the lint recognises a step only as a call to an identifier named `step`, with the body as its second argument.

### The read

The read is scoped to `#reveal`. The dry run shows why it may never widen to the document: the 2026-10-07 page's folio note reads "Cuetico, the capital. Once called Xiyicpec. ...".

```ts
import { seedForDate } from "../../../src/world/seed-of-the-day.ts";
import { makeSettle } from "../../support/settle.ts";
import type { Payload } from "../../types.ts";
import type { HuntKit } from "../hunt.ts";
import { huntQuarry } from "./quarry.ts";

// 2026-10-30: a day whose hunt quarry was renamed, Zodo once Tho (CI run 37379661660, and Issue #1084's dry run on the Mac's layout and on the runner's staged one), where HUNT_DAY's Xuacil never was.
export const FORMER_DAY = Date.UTC(2026, 9, 5, 12);
const FORMER_SEED = seedForDate(new Date(FORMER_DAY));
// 2026-10-30: this boot read 515 to 598 ms over 18 boots on the Mac (Issue #1084's dry run) and H1's boot of the same page about 0.9 s on CI (run 41114590473, lane A); 300 tries of at least 50 ms is h1Opens's 15 s, about 16 times the worse.
const BOOT_TRIES = 300;

type Booted = { seed: string | null; clues: number; hunt: boolean; solved: boolean };
const BOOTED: Payload<Booted> = `(()=>{const h=document.getElementById("hunt"),c=document.getElementById("clues"),m=document.getElementById("map"),svg=document.querySelector("#map svg");return{seed:svg?svg.getAttribute("data-vellum-seed"):null,clues:c?c.children.length:0,hunt:!!h&&!h.hidden,solved:!!m&&m.classList.contains("solved")};})()`;
const REVEAL: Payload<{ shown: boolean; text: string }> = `(()=>{const r=document.getElementById("reveal");return{shown:!!r&&!r.hidden,text:r?r.textContent:""};})()`;

export async function h5cFormerName(k: HuntKit): Promise<void> {
  const { evaluate, send, sleep, check, clickHunt, PORT } = k;
  await evaluate(`localStorage.removeItem("vellum.hunt.v1")`);
  await send("Page.navigate", { url: "about:blank" });
  await send("Page.navigate", { url: `http://127.0.0.1:${PORT}/seed-of-the-day/` });
  const settle = makeSettle({ evaluate, sleep, tolerant: true });
  await settle(
    BOOTED,
    (d) => d.seed === String(FORMER_SEED) && d.clues > 0 && d.hunt && !d.solved,
    "H5c the former-name day's hunt boots unsolved",
    BOOT_TRIES,
  );
  const tgt = await huntQuarry(k, FORMER_SEED);
  const won = await clickHunt(tgt.hit);
  const rev = await evaluate(REVEAL);
  check(
    "H5c on a day whose quarry was renamed, a live solve's reveal names what it was once called (#49, #1084)",
    tgt.formerName !== null && won.solved && rev.shown && rev.text.includes(`Once called ${tgt.formerName}.`),
    JSON.stringify({
      seed: tgt.seed,
      name: tgt.name,
      formerName: tgt.formerName,
      solved: won.solved,
      shown: rev.shown,
      text: rev.text.slice(0, 120),
    }),
  );
}
```
