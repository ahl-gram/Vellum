## The design

### A. Issue #1011: one key binding, in a new neutral module

- New module `src/site/shared/zoom-keys.ts` holds the one copy of: `ZOOM_STEP` (1.4), `PAN_FRACTION` (0.15, not exported), `glideMs()` (the `--glide` token reader, moved from `src/site/explorer/glass.ts` with its 300 fallback), and `bindZoomKeys(viewport, zoom, home)`, the keydown switch moved from `glassKeys` in `src/site/explorer/glass.ts`, with key `0` calling the `home` the caller hands in.
- `bindGlassKeys` in `src/site/shared/glass-keys.ts` keeps the `[data-zoom]` presses and the touch press, and takes its keys from `bindZoomKeys(viewport, zoom, () => zoom.glideHome())`.
- `createGlass` in `src/site/explorer/glass.ts` calls `bindZoomKeys(mapViewport, zoomController, goHomeVoiced)`; `glassKeys`, its `ZOOM_STEP`, `PAN_FRACTION` and `glideMs` are deleted from that file.
- Why the module is new and neutral: its path holds neither `glass-keys` nor `[data-zoom`, it queries nothing in the document, and it imports only a type, so `vellum/explorer-no-glass-keys` and the doctrine line stand unchanged, and the Explorer's bundle gains only the keys.
- Rejected: (1) the issue's own route, `bindGlassKeys` with an `onHome` hook imported into `glass.ts`: refused by `vellum/explorer-no-glass-keys`, and the import would bind the Explorer's presses twice through the document-wide `[data-zoom]` query. (2) Loosening the lint rule so `glass.ts` may import `glass-keys.ts` but not call the press binder: it weakens a guard the doctrine names as protecting a silent failure. (3) Leaving the duplicate: the issue exists to remove it.

### B. Issue #1010: one zoom room for six rooms, the shared framing camera for the seventh

- New module `src/site/shared/zoom-room.ts` with `bindZoomRoom(parts)`: `pageSlideAway` (step `ZOOM_STEP`), `createZoomController` (with `glideMs` and `onApply: (s) => slide.follow(s.k)`, scale extent left to the controller's default `[1, 8]`), `attach()`, `bindGlassKeys`, and `bindRoom` with `camera: framingCamera(zoom, viewport)`. Same order as all six rooms today: slide, controller, attach, keys, room. It returns `{ zoom, slide, room }`.
- Six rooms call it: the Print Room, the Prospect, the Ribbon, the Reading Room (`seats.ts` each), the Specimen Book (`src/site/specimen/app.ts`) and the Portfolio (`src/site/explorer/portfolio/app.ts`).
- The Daily Hunt (`src/site/seed-of-the-day/app.ts`) does NOT call it. `vellum/hunt-fixed-world` requires its controller be built in its own module with an options literal and no `onApply`, HZ4 (`test/site/hunt-zoom.test.ts`) witnesses that literal, its roster entry requires it to take `createZoomController` itself, and its slide-away takes a different shape (`fill`, `resting`, `camera`, frame `#map`). The Hunt takes only `framingCamera`, `ZOOM_STEP` and `glideMs` from the shared modules, and drops its `scaleExtent: [1, 8]` literal for the default.
- `src/site/explorer/camera.ts` moves to `src/site/shared/camera.ts` (Issue #1010 rules the move; `zoom-room.ts` in `shared/` would otherwise import from `explorer/`). It is NOT `src/site/home/camera.ts`, a different module that stays where it is. It gains `gestureBox(viewport)` (the rooms' `box()` with its zero guard) and `framingCamera(zoom, viewport)` (the `RoomCamera` pair every room but the Explorer holds the framing with).
- The framing hold changes behaviour in two rooms, fixed in this pull request by Alex's ruling (2) of 2026-10-31. The Reading Room and the Portfolio hold the raw `{ x, y, k }` today; both seat `#map-viewport` inside `#sheet` (`src/pages/reading-room/index.astro`, `src/layouts/ChartStage.astro`), so the gesture box changes size on every fit and a raw translate re-seated against it frames a different place. With `framingCamera` they hold the uv centre and depth, as the `RoomCamera` contract in `src/site/shared/room.ts` and the doctrine bullet "A refit restores the held FRAMING, never the raw transform" require. At home (k 1) the result is byte-identical: the held camera is `{ cx: 0.5, cy: 0.5, k: 1 }` and re-seats as `{ x: 0, y: 0, k: 1 }`. How far today's raw hold walks the framing in those two rooms was not measured: UNVERIFIABLE.
- `[1, 8]` after the change: one occurrence under `src/`, the default in `createZoomController`. `src/site/shared/zoom-controller.ts` is 452 lines and is not edited.
- `glideMs`: one reader, `glideMs` in `src/site/shared/zoom-keys.ts`, used by the Explorer, `bindZoomRoom` and the Hunt. The rooms' inline lambda had no fallback (an unset token gave NaN, which the controller's `glideMsNow` turned into 250); the shared reader falls back to 300, as the Explorer's always has. No page reaches that case: `src/styles/shared/motion.css` sets `--glide: 300ms`.
- Rejected: (1) the Hunt inside `bindZoomRoom` behind an option that skips `onApply`: the Hunt rule and HZ4 require the controller literal in the Hunt's own module, and the wrapper would hide it. (2) A named depth constant (`ROOM_MAX_K`): the controller's default already is the rooms' depth, and making the default read the constant edits a 452-line file this plan must not grow. (3) `ribbon`'s `lean` as a method on the zoom room: one caller, so it stays in `bindRibbonRoom` using `gestureBox` and `transformFromCamera`.

### C. What the new wrapper drags: two lint rules learn its name, one roster moves

- `bindZoomRoom` bundles both things two rules keep away from two surfaces: `bindGlassKeys` (kept off the Explorer and home by `vellum/explorer-no-glass-keys`) and a controller with an `onApply` (kept off the Hunt by `vellum/hunt-fixed-world`). Both rules read direct imports only, and each test declares "the kit reached through another module" as a blind spot. The wrapper makes that blind spot a named, obvious module, so each rule is taught the name `zoom-room`:
  - `vellum/explorer-no-glass-keys` refuses a `zoom-room` import the way it refuses a `glass-keys` one (the Portfolio stays exempt through `ROOMS_UNDER_THE_EXPLORER`, and it imports `zoom-room.ts` on purpose).
  - `vellum/hunt-fixed-world` refuses any import, re-export, literal dynamic import or held path string naming `zoom-room`, with its `hook` message.
- `SHARED_BINDINGS` (`scripts/lint/shared-bindings.ts`): the four rooms' three-binding entries become one `bindZoomRoom` binding each; `zoom-room.ts` gains an entry holding the three plus `framingCamera`; the Specimen Book joins with `bindZoomRoom`; the Portfolio gains `bindZoomRoom`; the Hunt gains `framingCamera`. Issue #779 ruling 3 kept "the checks that each room imports the shared camera, keys and sheet-fitting code"; Alex ruled on 2026-10-31 (ruling (1), Q1) that the check moves with the code, as written here.
- No new browser check. The framing math and the key table are what the code DOES (unit suite); that each room reaches the shared code is what the code SAYS (the roster lint); `check-placement.md` puts each rule in the cheapest instrument that sees it. The existing suites are run as regression evidence. So no build, probe or reading is owed for this plan.
