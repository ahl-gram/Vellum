## What this builds

A command a person or an agent runs on a comment sweep's branch before its pull request opens:

```
npm run keeper-scan -- diff <base> <head> [--dry-run] [--out <dir>]
```

`diff` collects every TypeScript comment run the branch deletes or trims, asks Jev the trial's seven keeper questions of each, asks each signal answered above 0.7 its own survival question against the whole file at head, and prints a report to paste into the sweep's ledger: the comments whose confident facts read as lost or unsettled, those skipped, and the sheets and pages it did not read. The comments Jev is unsure carry a keeper fact are counted and not listed (the ruling). There is no `trial` subcommand. No browser check, no lint rule, nothing in `npm test` calls Jev.

## The design

### Which comments are read

A deleted run is a comment run of a file at the merge base whose joined text no run of the same file at head carries: `addedRuns(path, headText, baseText)` in `scripts/comment-judge/collect.ts`, the comment judge's tested collector with its two texts swapped. The run keeps the base's line, text and `code` (the code beside it at the base). Every changed file is read through `changedFiles` in `scripts/comment-judge/tree.ts` from `mergeBase(repo, base, head)` to the head commit:

- an edited or renamed file whose head path `isTsUnderLintRoots` (`test-support/lint-roots.ts`) accepts is read, its base text at `Changed.before` and its head text at `Changed.path`;
- an added file has no deleted comment and is not named;
- an edited or renamed sheet or page (a path ending `.css` or `.astro`) is named NOT READ, since the command reads TypeScript only and the spec has a person scan those;
- a file the branch deletes (`deletedFiles`, new) is named NOT READ when `isTsUnderLintRoots` accepts it or it is a sheet or a page.

No run is filtered out: lint directives and runs under three words are asked like any other, since a two-word trailing comment (`// px`, `// -1 none`) is the spec's highest-value keeper class.

Measured on the PR #377 and PR #548 sweeps (revision 1's `out/1320-dry-run/population.log` at `9683c29e`, re-taken at fc6d7b03 through `isTsUnderLintRoots` in `out/1320-r2/dry.log`, with the same counts): the swapped collector finds 3,219 deleted runs (PR #377 2,067 in 291 files read, PR #548 1,152 in 272), against 1,869 under the experiment's rule (a run is removed when no run after keeps half its words, three words and up, directives out). Its extra 1,350 are comments the sweeps trimmed rather than cut: the population the per-signal survival question was written for ("a comment cut to one line keeps its warning and loses its measurement"). All 168 of Issue #1316's rows are among the 3,219. 42 of the 3,219 are under three words; none is a lint directive. No file of either sweep failed to parse; neither sweep deleted a file or touched a `.d.ts`.

**The blind spots, each named with its direction**:

- A deleted run whose exact text another run of the same file still carries reads as carried. It errs toward silence, and on these two sweeps it hid exactly one run (`out/1320-dry-run/live.log`: PR #548 `src/render/voyage-tour.ts:155`, "Reversing the whole cycle is cost-identical; orientCycle owns that choice.", whose identical text stands elsewhere in the file at head, so the fact does survive in its file, which is what the scan asks).

### The questions, frozen

`scripts/keeper-scan/questions.ts` holds the trial's fourteen questions exactly as `out/1304-exp/questions.ts` (`KEEPERS`) and `out/1304-exp/survival-all.ts` (`SURVIVAL`) in the main checkout hold them. Every question is `{ type: "noul", instructions, criteria: { true, false } }`, in that key order, built by a local `noul(instructions, yes, no)`. The keys of both records are in this order: `measured`, `platform`, `deviation`, `golden`, `units`, `convention`, `sentinel`.

`KEEPERS` (state `{ comment, file, code }`, built by `stateOf` in `scripts/comment-judge/questions.ts`):

| signal | instructions | criteria.true | criteria.false |
|---|---|---|---|
| measured | Does `comment` give a number that someone measured, swept or tuned by hand? | `comment` states a value found by measuring or trying, such as a timing, a pixel width, a worst case seen across seeds, or the range a sweep covered. | `comment` states no number, or only a number that `code` already shows, with nothing about where it came from. |
| platform | Does `comment` describe how software outside this repository behaves, such as a browser, Node, git, a CI runner or a library? | `comment` says what an outside tool does, for example that headless Chrome lays out at a different width than asked, or that a git command strips a character. | `comment` talks only about this repository's own code and data. |
| deviation | Does `comment` say that `code` departs on purpose from a rule, a ruled design, or the obvious way to write it? | `comment` warns the reader that the code is deliberately unusual, for example a value kept different from the mockup on a ruling, so the reader does not change it back. | `comment` describes code written the ordinary way, with no warning against changing it. |
| golden | Does `comment` say that some output must stay byte-identical, such as a golden file, a committed chart or a seed's world? | `comment` says a change here would move bytes that are pinned, for example that a committed chart or the golden depends on this order. | `comment` says nothing about output that must stay the same byte for byte. |
| units | Does `comment` name the units or the scale of a value in `code`? | `comment` says what a bare number is measured in, for example cells, pixels, milliseconds, degrees or a fraction of the sheet width. | `comment` names no unit, or the unit is already in a name in `code`, such as `timeoutMs`. |
| convention | Does `comment` say which way a coordinate, an index or a direction runs in `code`? | `comment` states an orientation, for example that y grows downward, that row comes before column, or that an angle is measured clockwise from north. | `comment` states no orientation or ordering convention. |
| sentinel | Does `comment` say what a special value in `code` stands for? | `comment` decodes a marker value, for example that -1 means no basin, that null means the sea, or that 0 means unset. | `comment` decodes no special value. |

`SURVIVAL` (state `{ comment, file, file_after }`, `file_after` the WHOLE file text at head):

| signal | instructions | criteria.true | criteria.false |
|---|---|---|---|
| measured | Does `file_after` still say how the number in `comment` was measured or found? | `file_after` keeps the provenance `comment` gave, such as what was measured, over how many cases, on which date or issue, even in fewer words. | `file_after` may keep the number and its meaning, but no longer says how or where it was measured or found. |
| platform | Does `file_after` still say how the outside tool behaves that `comment` describes? | `file_after` keeps the fact about the browser, Node, git, the CI runner or the library that `comment` gave, even in fewer words. | `file_after` keeps the code, but no longer says what the outside tool does. |
| deviation | Does `file_after` still warn that the code departs on purpose, as `comment` did? | `file_after` still tells the reader the unusual choice is deliberate, so it should not be changed back. | `file_after` keeps the code, but nothing in it says the choice was deliberate. |
| golden | Does `file_after` still say that the output must stay byte-identical, as `comment` did? | `file_after` still says a change here would move pinned bytes, such as the golden or a committed chart. | `file_after` keeps the code, but no longer says any output depends on it byte for byte. |
| units | Does `file_after` still name the units or the scale that `comment` gave? | `file_after` still says what the value is measured in, in a comment or in a name such as `widthPx`. | `file_after` keeps the value, but nothing says what it is measured in. |
| convention | Does `file_after` still say which way the coordinate, index or direction runs, as `comment` did? | `file_after` still states the orientation or ordering `comment` gave. | `file_after` keeps the code, but no longer states the orientation or ordering. |
| sentinel | Does `file_after` still say what the special value means, as `comment` did? | `file_after` still decodes the marker value, in a comment or a name such as `NO_BASIN`. | `file_after` keeps the value, but nothing says what it stands for. |

### The bands

A keeper answer above 0.7 flags its signal, and only a flagged signal is asked its survival question or listed. A survival answer under 0.3 reads as lost, from 0.3 to 0.7 unsettled, above 0.7 still said. A keeper answer from 0.3 to 0.7, both ends included, is unsure: it is never asked and never listed (the ruling, menu 1 option C). The thresholds are `YES` (0.7) and `NO` (0.3), imported from `scripts/comment-judge/questions.ts`. A comment's band, first match wins:

1. **lost**: a flagged signal's survival answer is under 0.3;
2. **unsettled**: a flagged signal's survival answer is from 0.3 to 0.7;
3. **still said**: at least one signal is flagged and every flagged one survives above 0.7;
4. **unsure**: no signal is flagged and at least one keeper answer is from 0.3 to 0.7;
5. **no signal**: every keeper answer is under 0.3;
6. **skipped**: a call failed or the run's token cap was reached; nothing is claimed for it.

Lost, unsettled and skipped comments are listed with their text; still said, unsure and no signal are counted only. The exit code says nothing about losses: 0 when every comment was read, 1 when any was skipped, 2 on a usage error; a thrown error (a git failure, a file that does not parse) prints its message and exits 1.

On the two old sweeps (`out/1320-dry-run/ruled-c.log`, command `node out/1320-dry-run/ruled-c.ts`, no Jev call, re-reading `live.ts`'s replies): of 3,219 comments, lost 196, unsettled 290, still said 399, unsure 1,304, no signal 1,030; listed 486 (15.1%), about 8 of every 50, the figure the ruling was given.

### The report

Printed to stdout, each line exactly as below, `<n>` a count, `<k>` a keeper answer and `<s>` a survival answer at two decimals (`two` in `scripts/comment-judge/report.ts`):

```
deleted comments read at <base sha>, their files at <head sha>; answered by <models>
LOST <file>:<line>: <signal> (keeper <k>, survival <s>); <signal> (keeper <k>, survival <s>)
  > <the comment's joined text at the base>
UNSETTLED <file>:<line>: <signals, as above>
  > <text>
SKIPPED <file>:<line>: <reason>
  > <text>
NOT READ <path>: <reason>
keeper-scan: <n> deleted comments; lost <n>, unsettled <n>, still said <n>, unsure <n> (not listed), no signal <n>, skipped <n>; files not read <n>
```

- Every LOST line first, then every UNSETTLED, then every SKIPPED, each group in collection order (file order, then line); then every NOT READ line; then the summary. A comment's signals are every flagged signal, in the record order, joined by `; `.
- `<models>` is `modelsOf` in `scripts/comment-judge/report.ts` over the replies (`none` when nothing answered).
- When skipped is above 0, the summary's `skipped <n>` is followed by ` (a skipped comment was not read, so it is scanned by hand)`.
- The two NOT READ reasons are the exported constants `BY_HAND = "a sheet or a page, which this scan does not read, so its deleted comments are scanned by hand"` and `DELETED_FILE = "the branch deletes the file, so no file is left to read its comments against"`.
- `<file>` is the head path; `<line>` is the run's line at the base.

A dry run sends nothing (`dryRunSender`), so every comment is skipped at its keeper request, and prints every NOT READ line, then one line:

```
dry run: <n> deleted comments, <n> keeper requests, <7n> questions, <characters> characters; the survival questions follow the keeper answers, so none was built; nothing was sent
```

`<7n>` is the sum of `Object.keys(request.questions).length` over every request built (seven a comment, since a dry run stops each at its keeper request), and `<characters>` the sum of `JSON.stringify(request).length` over the same requests. `--out <dir>` writes `requests.jsonl` and `replies.jsonl` through `writeAll` in `scripts/jev/cli.ts`, their lines made by `requestLines` and `replyLines` in `scripts/comment-judge/report.ts`: one JSON object a line, `{ "sha", "comment": "<file>:<line>", "request": <1-based within the comment>, "body" }` and the same with `"reply"` for `"body"`, `sha` being the merge base the comment's line is read at (each request's `state` carries the comment's text and the code or file it is asked about). The key is never in either: `ask` in `scripts/jev/system-one.ts` puts it in a header only, and R2 holds the report and both logs to it.

### No self-check

There is no `trial` subcommand, trial set or reference score (the ruling, menu 2 option C), and nothing else in this plan needs one: the token cap is derived from single `diff` runs, and the acceptance run is a `diff` of the PR #548 sweep (Evidence). The questions are frozen by Q1 and Q2. A pull request that changes their wording changes those digests and says so in its body.

### Spend and failure

- Requests go one at a time through `sendFor` in `scripts/jev/cli.ts` (`liveSender`, the key from `TYPESAFE_API_KEY`, then `~/.config/typesafe/key`, never printed), with no retry: a failed call skips its comment, the run exits 1, and the person runs it again.
- `RUN_INPUT_TOKEN_CAP` in `scripts/keeper-scan/scan.ts` is `8_000_000`, on the one dated line `// 2026-11-10: about twice the 3,940,154 input tokens the PR #377 sweep's diff took at jev-1.14.0 in the Issue #1320 planner's run, the largest single run measured; the first weekly sweep's whole range is about 2.6 million.` Once the input tokens the replies report reach it, every comment after is skipped unsent with the reason `capReason(cap)` from `scripts/jev/system-one.ts`, which reads `the input-token cap of 8000000 for this run was reached`.
- A file the service will not take whole (`HTTP 400: {"detail":{"error_type":"max_tokens_exceeded"}}`) skips the comment asked against it, with that reason, like any failed call. At main the service took `test/site/astro-scaffold.test.ts` (61,675 characters) and refused `src/prospect/letter/face-italic.ts` (66,071) and `src/world/outline-place-ids.ts` (84,723), generated files no sweep cuts a comment from.

## Alternatives rejected

- **The experiment's half-the-words rule for a deleted comment**: it misses every comment a sweep trimmed but kept half of, 1,350 of 3,219 on the two old sweeps, which is where a measurement is cut and its warning kept.
- **Counting text and the code beside it** (a multiset of text plus first code line): it adds one run over both sweeps, and that one's fact stands elsewhere in its file, so it does not earn a new function.
- **Filtering runs under three words and lint directives**, as the experiment's sample did: the short trailing comment is the spec's highest-value keeper class, and it costs 42 small requests over both sweeps.
- **Listing the unsure band, or asking it the survival question too**: ruled out (menu 1, option C).
- **A `trial` subcommand against Issue #1316's rows, or a hand-labelled set**: ruled out (menu 2, option C).
- **Dropping the unsettled comments too, listing only survival answers under 0.3**: the option ruled listed 486 of 3,219, about 8 of 50, which counts the unsettled; listing only the lost would be 196, about 3 of 50, a different option from the one Alex confirmed with its cost.
- **Cutting `file_after` to fit a size bound**: a fact past the cut would read as lost, and the spec's question is whether the fact survives anywhere in its file. A file the service refuses is skipped, which the report says.
- **A bare `npm run keeper-scan -- <base> <head>`** (the issue's form): every house Jev command takes a subcommand naming what it reads (`npm run comment-judge -- diff`, `npm run recon-triage -- rank`, `npm run copy-hunt -- diff`), and Issue #1324's skill is written against `diff`.
- **Running the requests in parallel with retries** (the experiment's 4 to 6 workers and four backoff tries): the planner's 5,408 sequential requests met no failure the service did not mean, the larger old sweep takes about five minutes one at a time, and a weekly sweep a minute or two; parallel workers and a backoff are code with nothing measured for them to fix.
