## The design

### 1. The tree, as typed data, in `src/layouts/nav.ts` beside `NAV_ITEMS`

- `NAV_ITEMS` unchanged (seven, same order, same labels).
- `ROUTE_NAMES: Record<route, string>`: the name each route goes by in the trail, keyed by route, the root included (`"/": "Vellum"`). The names are the rooms' own (`"/faq/": "Questions & Answers"`, `"/ribbon/": "The Wayfarer's Ribbon"`).
- `ROUTE_CHILDREN: Record<parent route, readonly route[]>`: `"/explorer/": ["/prospect/", "/ribbon/", "/print-room/portfolio/"]`, `"/reading-room/": ["/prospect/"]`. The Portfolio sits at its CURRENT address until Sub 4 (Issue #669) moves it; the trail reads "Vellum › The Explorer › The Portfolio" over `/print-room/portfolio/` meanwhile, as the issue expects.
- The top level is `NAV_ITEMS` itself, never restated. A route's SEAT is its first appearance walking the nav in order, each room's children after it; every later appearance is an ALIAS. Derived from order rather than carried as a flag (the mock carries both an `alias: true` flag and the order, which agree only by construction), so the two cannot disagree.
- Pure helpers in the same file: `seatOf(route)` (the parent route; null at the top level; undefined when unseated), `aliasesOf(route)`, and `trailFor(path)` returning `{ crumbs: [{name, href}], current, also: [{name, href}] }` or null. `current` is true exactly when the page is not on `NAV_ITEMS`, which is the one-mark rule. Home (the root) and any unseated route (the Specimen, the atlas) return null. A seated route with no name throws, so a missing name is a build error the way a missing blurb is in `scripts/generate-discovery.ts`.
- ONE source of names for the trail, `ROUTE_NAMES`, and every existing copy pinned to it by tests: each page's `const room` (the scaffold's literal per-page trail, whose last name must equal the page's `room`, which the existing "titles are computed in the layout from the room" test already ties to the page's const); `ROUTE_ENTRIES` titles in `scripts/generate-discovery.ts` (a unit test: every seated route's title equals its tree name, home's equals the root's); and the road buttons, whose `room` names their destination (11 literal props in 7 page files, plus the Seed of the Day's two from its `roads` data), pinned on the RENDERED pages: every `a.legend-btn`'s `span.room` equals `ROUTE_NAMES` of the route its href resolves to. Deriving discovery's titles from the tree instead would restructure `ROUTE_ENTRIES`, which also carries home and the atlas, for no change in output; the issue asks for one source with the others pinned.

### 2. The trail, drawn by `src/layouts/BaseLayout.astro` inside `header.chrome`, right after `nav.rooms`, before the unused `<slot name="header-extra" />`

The issue says the trail goes "in" that slot. A slot is filled by a PAGE; the trail is derived from the layout's own `path` and must be identical on every page, so the layout draws it at the slot's seat rather than having ten pages fill a slot with the same call. The slot stays for Sub 6 or is the next thing to use it. This is a call (below).

Markup lifted from `directionC` in `design/nav-wayfinding/directions.mjs`, written on one template line so no whitespace text node lands between inline segments (the mock joined them with none, and so does the live nav):

```
<nav class="trail" aria-label="Where you are"><a href="/">Vellum</a><span class="way" aria-hidden="true">›</span><a href="/explorer/">The Explorer</a><span class="way" aria-hidden="true">›</span><span aria-current="page">The Prospect</span></nav><p class="also">also reached from <a href="/reading-room/">The Reading Room</a></p>
```

Every segment but the last is a link with a root-absolute href (shell-owned links are root-absolute, `handbook/specs/site-architecture.md` "Link form is scoped"); the last is `<span aria-current="page">` on a page that is not on the nav (the Prospect, the Ribbon, the Portfolio) and `<span class="here">` on a top-level room, whose mark the nav already carries. No trail on home or the Specimen. The trail sits OUTSIDE `nav.rooms`, so the doors reads (`DRAWER_READ` in `e2e/suites/cluster.ts`, `READ` in `e2e/suites/room-drawer.ts`) and the literal 7 in `stacked` in `e2e/suites/cluster.ts` are untouched. Links need no allowlist change: `header.chrome a` already takes the hand back and `header.chrome a:focus-visible` already recolours the ring.
