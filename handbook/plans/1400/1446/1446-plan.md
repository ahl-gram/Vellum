## The design

### The camera's target (Issue #1448; Q1, ruled: "The wait finds it itself")

`framed` stops taking a target. It finds the camera's own sheet itself, by where the sheet sits: `CAMERA_TARGET = "#map-viewport > #map, #map-viewport > .rf-chart"`, the direct child of the gesture box that every zoom room's controller writes (`targetEl` in `src/site/shared/zoom-controller.ts`; the `targets` reading). The Reading Room's own `g#map`, inside the chart's SVG, is never a child of the box, so it can never be watched. An empty box (no child at all) keeps reading as a camera at rest, as `RR_LENS`'s sentinel was made for. A box that holds something but no target the selector knows makes the in-page script throw `no camera target in #map-viewport`, which the harness's `evaluate` raises (`eval exception: ...`), so the wait reds its step instead of handing over early: the one way a future room with another layout could otherwise degrade silently. No caller passes a target any more, so a lens and a target can no longer disagree: `lensRest` and `homeCamera` lose their `on` parameter, and the Reading Room's three pass-throughs, `pressGlass`'s ternary and `zoomIn`'s `on` go. A wrong lens can still be passed, and then only the read is wrong, which the check's own assertion sees (RR40 asserts k 1.4); the rest itself is held by the writes on the real target.

### `kStill` (Issue #1446; ZG6, ZG7, ZG11)

A wait for a camera that is meant never to move has no departure to ask for, so it waits on the engine's clock instead: the same k and no camera write across `STILL_FRAMES = 2` drawn frames since the read that began the quiet run. Any read whose k or write count differs from that anchor starts the run again. Two, because a glide d3 starts writes on its timer's first frame unless that tick lands at the glide's very start, where the transform it writes equals the one standing and the style records no change; the second frame is then the first that must write. The poll spacing no longer matters, which is the point: main's six reads 50 ms apart fit inside one of the runner's frame gaps (up to 247 ms, `handbook/plans/1300/1365/1365-plan.md`). Each caller's own delivery wait stands before it (ZG7's double click reached the box; ZG6's fingers reached and lifted), and ZG11's double tap is delivered by the time `doubleTap` returns (the `zg` reading counted both touchends in 9 of 9 cycles), so no wait is added there.

### P23 and CD48 (Issue #1446)

Each takes `framed` and `landedWith`, as `kLeft` does, through a named wait of its own module so a unit test can drive it: `cardAtDepth` in `e2e/suites/cards/cap.ts` (departure: k above 1.05, rest: k and the card's height equal across a drawn frame with no camera write) and `cameraAtRest` in `e2e/suites/chart-drawer/floor.ts` (rest: x, y and k equal across a drawn frame with no camera write; no departure, as `camBefore` has none today).

### Rejected

- **Issue #1448's first exit, a `framed` that refuses an absent target**: in the Reading Room `#map` is present (the chart's `g`), so a dropped Reading Room target is never refused, and the wait falls back to two equal reads across a drawn frame, with no write ever counted (the `rrdrop` "target-dropped" rows waited for the landing on the Mac; the runner's long gaps are where that shape handed over early before PR #1445). Option A keeps the refusal's intent where it bites: a box holding an unknown child.
- **Issue #1448's second exit, one value carrying lens and target**: a mismatched pair cannot be passed, but a dropped value falls back to the default pair, which in the Reading Room is the `rrdrop` "both dropped" case: RR40's lean reds (its k reads 1), and `homeCamera`'s home wait hands over mid-glide with no red.
- **`kStill` keeping six reads with the frame witness on each pair** (the issue's first suggestion): counting consecutive pairs that each span a frame resets the count on every pair taken inside one frame gap, so on the runner's 100 to 250 ms frames six in a row would rarely come; the frames, not the reads, are the clock.
- **`kStill` as `kLeft`'s shape with a departure** (the issue's second): the camera is meant not to move, so there is nothing to depart on.
- **`kStill` on one frame**: the start tick that writes no change is one frame.
- **Waiting on d3's `__transition` or the Explorer's `__vellumCameraSettling`**: as `handbook/plans/1300/1365/1365-plan.md` rejected them.
- **Folding the two other in-page frame counters into `camera-landed.ts`** (Issue #1446 leaves it open): `FRAMES_ON` in `e2e/suites/broadside/grow.ts` logs every frame's k and bill height as its check's own evidence, which `framed` does not keep, and `COUNT_FRAMES` in `e2e/suites/cards/cap.ts` is a scroll's clock with no camera target. Not folded (call C6).

### `e2e/support/camera-landed.ts`, whole, after the change

```ts
import type { Payload } from "../types.ts";

export type Framed<T> = { read: T; frames: number; writes: number };

export const CAMERA_TARGET = "#map-viewport > #map, #map-viewport > .rf-chart";

export const framed = <T>(read: Payload<T>): Payload<Framed<NonNullable<T>>> =>
  `(() => { const e = document.querySelector(${JSON.stringify(CAMERA_TARGET)}); if (!e && document.querySelector("#map-viewport > *")) throw new Error("no camera target in #map-viewport"); let w = window.__cameraWatch;
  if (!w || w.target !== e || !w.on) { if (w && w.on) w.stop(); w = window.__cameraWatch = { target: e, frames: 0, writes: 0, on: true };
    const obs = new MutationObserver((rs) => { w.writes += rs.length; }); if (e) obs.observe(e, { attributes: true, attributeFilter: ["style"] });
    const tick = () => { if (!w.on) return; w.frames++; requestAnimationFrame(tick); }; requestAnimationFrame(tick);
    w.stop = () => { w.on = false; obs.disconnect(); }; }
  return { read: (${read}) || null, frames: w.frames, writes: w.writes }; })()`;

export const STOP_CAMERA_WATCH: Payload<boolean> = `(() => { if (window.__cameraWatch && window.__cameraWatch.on) window.__cameraWatch.stop(); return true; })()`;

export const landedWith =
  <T>(same: (d: T, last: T) => boolean, frames = 1) =>
  (d: Framed<T>, last: Framed<T>): boolean =>
    d.read !== null &&
    last.read !== null &&
    same(d.read, last.read) &&
    d.writes === last.writes &&
    d.frames - last.frames >= frames;
```

## Rulings, as folded (Issue #1448 comment 7142291963)

- **Q1, "The wait finds it itself" (option A)**: the design above is the build. `framed` takes no target and always watches `CAMERA_TARGET`; `lensRest`, `homeCamera` and the Reading Room's pass-throughs lose their target argument; a gesture box holding anything else stops the wait with an error. Options B, C and D were put to Alex and not taken. The menu as he read it, kept as the record:

**Q1 (Issue #1448): how should a camera wait know which part of the page to watch?** Today each wait is told which element the camera moves, and the Reading Room's waits are told a different one. If a Reading Room call forgets to say so, the wait watches an element that never moves, so it can no longer tell a camera still gliding from one at rest, and nothing reports the mistake.

- **A. The wait finds the moving sheet by itself (Recommended; ruled).** Every room's camera moves the one sheet that sits directly inside the chart's frame; the wait looks there, in every room, and no call names an element at all. Measured: in all nine zoom rooms that is exactly the element the camera moves, and nothing else ever sat in that frame while each room started, zoomed and redrew its chart. Consequence: the mistake becomes impossible; the two shared waits and the Reading Room's calls lose the argument; a room built later with a different layout makes its waits stop with an error instead of guessing.
- **B. The issue's first idea: refuse an element that is missing.** Consequence: it never notices the case the issue was filed for. Measured: in the Reading Room the wrong element is not missing, it is the chart's own drawing group, so a forgotten Reading Room argument is never refused. The wait then settles for two matching readings a frame apart: on this Mac that still waited for the camera to stop (2 of 2), and on GitHub's slower machines it is the kind of wait that finished early before the last fix (not reproduced here).
- **C. The issue's second idea: carry the camera reading and its element together as one value.** Consequence: a mismatched pair can no longer be passed, but a forgotten value falls back to the ordinary rooms' pair. In the Reading Room the check that the zoom button magnifies the chart would then fail loudly, while the clean-up wait that sends the camera home finished early with no error: measured, it let go at 153 ms with the camera still moving (2 of 2).
- **D. Leave it as it is.** Consequence: no code changes and Issue #1448 closes as a known risk; nothing names the wrong element today, and a future slip would stay silent.
