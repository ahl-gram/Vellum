## The design, and what was rejected

### How the hook knows it is inside a headless build

The wrapper sets the environment variable `VELLUM_HEADLESS_BUILD` to the issue number on every `codex exec` and `codex exec resume` it starts. Codex hands its own environment to the hook process: measured by this planner (`out/1409-dry-run/notes.md` in the planner's tree, runs A and B, at `c435586c`): with the variable set on the `codex` process, the hook saw `marker: "from-codex-env"`; on a resume of the same thread launched without it, `marker: null`. Only `runCodexHook`, the Codex adapter's entry, reads it, and passes it into the request as `headlessBuild`; the engine, the checks and the Claude adapter never read the environment for it. The model's own shell sees the variable too (run A printed it), which is why no test helper and no shared module may read it: a headless build running `npm test` would otherwise judge the hook's own fixture rows as a build.

Rejected:
- **The payload's `permission_mode`**, which read `bypassPermissions` in run A. What an interactive session started with `-a never` reports was never measured, so it cannot be shown to mark headless builds alone.
- **Reading `source: "exec"` from the session file the payload's `transcript_path` names**: an undocumented file read on every call, and it would also mark every hand-started `codex exec` probe.
- **Refusing in every Codex session**: ruling 3 scopes the refusal to a headless build, and an interactive Codex session keeps its own flow.
- **A second entry in `.codex/hooks.json`, or a second launcher**: that file is frozen, pinned byte for byte by `test/repo/codex-hook.test.ts`, and any change to it drops Alex's trust until he re-trusts it in `/hooks`. The refusal lives in the launcher's code, which the frozen command already runs, so nothing needs re-trusting.

### What the refusal covers

Inside a headless build: `git push` in any form `gitCall` reads; `npm run proof` (an `npm run` option before `proof` included) and `node scripts/proof-runner/main.ts`, since a proof run pushes a `proof/` branch and starts a workflow; and every `gh` call that is not on a read list. It is judged before every other refusal, so the build is told why it cannot rather than handed another way to post (the existing `gh api` refusal's reason recommends `/comments`).

The read list: `gh api` whose last method is GET, or that carries no method and no data field; `gh pr view|list|checks|diff|status`; `gh issue view|list|status`; `gh run view|list|watch`; `gh repo view`; `gh release view|list`; `gh workflow view|list`; `gh label list`; `gh search issues|prs|code|commits|repos`; `gh auth status`; `gh` alone or with `--version`, `--help`, `-h`, `version` or `help` as its first word.

Rejected: **a list of named writes** (`gh pr create`, `gh issue comment`, ...). A `gh` command the list forgot would pass silently; a read list errs toward refusing, which is visible and one edit away.

### Who builds the tree, and who is the implementer inside the build

The wrapper builds the tree `.claude/worktrees/codex-<issue>` in the main checkout, as workflow step 7 builds one for a session with no isolation (fetch, `worktree add --detach ... origin/main`, the `node_modules` link), by `createPlan` from `scripts/agent-sandbox.ts`, so no copy of that recipe is written. The Codex implementer's own definition already expects this: its `implementer-tree` slot in `handbook/agents/adapters/codex-local.md` says the dispatcher made the tree and names it in the prompt, and its `implementer-branch` slot has it run `git switch -c` itself.

Inside the build, the `codex exec` session itself is the implementer: its prompt tells it to read `.codex/agents/vellum-implementer.toml` and follow it, with headless overrides. Issue #1400 was built the same way, by a Codex main session. The model and the effort are the role's from `.agents/model-policy.json`, passed on every run as `-m <model>` and `-c model_reasoning_effort="<effort>"` (Alex, 2026-11-20). Run C measured `-m gpt-6.2-sol` working headless, and runs E and F that the effort override takes on a build and, restated, on a resume (the session file recorded `medium`, then `low`, against the user default `high`).

Rejected: **the exec session spawning the `vellum-implementer` role** by name. Unmeasured headless; a resume by thread id would reach the parent and not the role; and the role's commands may not appear in the parent's `--json` stream, which is what Alex follows.

### What the build is told, and how it ends

The prompt (`scripts/handoff/prompt.ts`, its text under Files below) carries the plan, the tree, the session the trailers name, and the overrides the role body does not know: commit only; write what would be posted into the record's folder (`record.md`, `pr-body.md`, `guards.md`); stop where the definition would dispatch the guard prover or the plate reader, or open the pull request, whichever comes first; and end the last message with exactly `OUTCOME: ready` or `OUTCOME: handback`. Its first command is a hook check: `git push --dry-run origin HEAD:refs/heads/handoff-hook-check`, which the hook must refuse. That stands in for `CLAUDE.md`'s `/hooks` check, which a headless run cannot make, and it proves exactly the refusal this issue adds; where the hook is not live it runs as a dry run and writes nothing.

Rejected: **changing the implementer's role body** to carry the headless overrides. It would make this pull request change two generated agent definitions (workflow step 14's disclosure, a regeneration), for text only a headless build needs and that the wrapper's prompt already carries.

### The build's record

Everything for one build sits in `out/<issue>-handoff/` in the main checkout: `state.json` (the record the wrapper keeps), `run-<n>.jsonl` (the `--json` stream, which Alex follows with `tail -f`), `run-<n>.stderr.txt`, `run-<n>-last.md` (the last message), and the files the build and the session write (`record.md`, `pr-body.md`, `guards.md`, `prover-report.md`, `implementer-proof.md`). Delivery folders already live in the main checkout's `out/`, and so does Codex's scratchpad.

### `next`, step by step

`next` gathers a snapshot (the label, the record, whether the last run's wrapper is alive, the last run's outcome line, the tree's branch and head, the branch's pushed head, whether `prover-report.md` exists, the pull request) and a pure function picks the step:

1. no record, no label: `claude-builds`;
2. no record, labelled: `plan`;
3. the last run has no end and its wrapper process is alive: `running`;
4. the last run handed back: `replan`;
5. the last run has no outcome line (or its wrapper died): `stopped`;
6. ready, but the tree is on no branch: `stopped`;
7. the pull request is merged: `retire`; closed unmerged: `closed`;
8. the tree's head is not the pushed head: `push`;
9. the pull request is open: `review`;
10. no prover report yet: `prove`;
11. otherwise: `open-pr`.

```ts
export type Io = {

  readonly stream: string; readonly stderr: string;
};
export const runCodex = (argv: readonly string[], io: Io): Promise<number>;
export type Outcome = "ready" | "handback";
export const outcomeOf = (lastMessage: string): Outcome | null;
export const threadOf = (stream: string): string | null;
```

- `D2_FLAGS` go before the subcommand on both launches: `codex exec` rejects `-a`, and `codex exec resume` takes no `-s`, so a resume that left them out ran `workspace-write` (round 1, comment 7030297606). `exec resume` takes no `-C` either (`codex exec resume --help`), so `runCodex` runs it with the tree as its working folder.
- The effort goes as `-c` with the key `model_reasoning_effort` and the value a quoted TOML string (`model_reasoning_effort="high"`, one argument, no shell), on both launches: each run takes its own (runs E and F), and whether a resume keeps an earlier run's was not measured, so it is never left to. It is the only `-c` the wrapper passes, and `CLAUDE.md`'s Codex section names it as the one allowed (Rosters and doctrine).
- `runCodex` spawns `codex` with `stdio: ["ignore", <stream opened "w">, <stderr opened "w">]`, `cwd: io.cwd` and `env: io.env`, and resolves with the exit code; 127 when the process cannot start (its message written to the stderr file), 1 when it ends on a signal. Stdin is `ignore` because an open stdin stalls `codex exec` at "Reading additional input from stdin..." with no error (round 1, finding 7).
- `outcomeOf` reads the last non-empty line, trimmed; `ready` for exactly `OUTCOME: ready`, `handback` for exactly `OUTCOME: handback`, null for anything else, an empty text included.
- `threadOf` returns the `thread_id` of the first line whose JSON has `type` `thread.started`; a line that does not parse is skipped; null when there is none.

**`scripts/handoff/next.ts`**

```ts
export type PullRequest = { readonly number: number; readonly state: "OPEN" | "MERGED" | "CLOSED" };
export type Snapshot = {
  readonly issue: number; readonly root: string; readonly folder: string;
  readonly builder: "codex" | "claude"; readonly state: HandoffState | null;
  readonly running: boolean; readonly outcome: Outcome | null;
  readonly branch: string | null; readonly treeHead: string | null; readonly remoteHead: string | null;
  readonly proverReported: boolean; readonly pr: PullRequest | null;
};
export type StepId =
  | "claude-builds" | "plan" | "running" | "stopped" | "replan" | "push"
  | "prove" | "open-pr" | "review" | "retire" | "closed";
export type Step = { readonly id: StepId; readonly text: string };
export const nextStep = (s: Snapshot): Step;
```

The checks run in the order "`next`, step by step" gives. In the texts, `run` is `lastRun(state)`, `files` is `runFiles(folder, run.n)`, `tree`, `plan` and `thread` come from the record, and "unpushed" means `branch !== null && treeHead !== remoteHead`. Each text, exactly:

- `claude-builds`: `Issue #${issue} carries no builder:codex label, so Claude Code builds it: dispatch vellum-planner on it, then vellum-implementer on its finished plan (handbook/specs/orchestration.md). The wrapper launches nothing for it.`
- `plan`: `Issue #${issue} is labelled builder:codex and has no build yet. Dispatch vellum-planner on it, and once its plan is finished and archived (handbook/specs/orchestration.md), run in the background: npm run handoff -- build ${issue} --plan <the plan's scratchpad path> --session <this session's link>`
- `running`: `Run ${run.n} (${run.kind}) of Issue #${issue} is running in ${tree}, thread ${thread ?? "not started yet"}. Alex can follow it with: tail -f ${files.stream}. Wait for the background task's notice.`
- `replan`: `Run ${run.n} of Issue #${issue} handed back: ${files.last}.` then, when unpushed, ` First push its commits: git -C ${tree} push -u origin ${branch}.`, then ` Then dispatch a fresh vellum-planner with the issue, the plan ${plan} and that hand-back (handbook/specs/orchestration.md). Once its revision is finished and Alex has seen it, write a brief naming it and run in the background: npm run handoff -- resume ${issue} --brief <the brief's path> --plan <the revision's path>`
- `stopped` with no outcome: `Run ${run.n} of Issue #${issue} ended without its outcome line (exit ${run.exit ?? "none recorded"}). Read ${files.last} and ${files.stream}, and put what they show to Alex. Once he rules, write a brief and run in the background: npm run handoff -- resume ${issue} --brief <the brief's path>` then, when `thread` is null, ` No thread started, so it cannot be resumed: retire ${tree} and move ${folder} aside before building again.`
- `stopped` on no branch: `Run ${run.n} of Issue #${issue} says it is ready, but ${tree} is on no branch. Read ${files.last} and put it to Alex.`
- `retire`: `Pull request #${pr.number} merged. Retire Issue #${issue}'s build: rm ${tree}/node_modules, then git -C ${root} worktree remove --force ${tree}, then move ${folder} aside as ${folder}-${pr.number}, which keeps the record and lets a later pull request of the issue build.`
- `closed`: `Pull request #${pr.number} for Issue #${issue} was closed without merging. Ask Alex what becomes of the build in ${tree}.`
- `push`: `Run ${run.n} of Issue #${issue} is ready and not pushed. Push it: git -C ${tree} push -u origin ${branch}` then, with a pull request, `; pull request #${pr.number} updates with it.`, and without one, `, then run npm run handoff -- next ${issue} again.`
- `review`: `Pull request #${pr.number} is open for Issue #${issue}. Once Alex rules on the cold skeptic's findings, write the fixes he named into a brief and run in the background: npm run handoff -- resume ${issue} --brief <the brief's path>. Nobody runs the skeptic or a used prover again; with nothing to fix, it waits for his merge.`
- `prove`: `Issue #${issue}'s build is pushed on ${branch}. Prove its guards (${folder}/guards.md) as handbook/specs/orchestration.md says, saving the prover's report unedited as ${folder}/prover-report.md.`
- `open-pr`: `The prover's one round for Issue #${issue} is in ${folder}/prover-report.md. Once every required guard has a shown bite (that report, and ${folder}/implementer-proof.md for any the build proved), post ${folder}/record.md on the issue, complete ${folder}/pr-body.md and open the pull request from ${branch} with it, then dispatch vellum-pr-skeptic cold with its number.`

**`scripts/handoff/snapshot.ts`**

```ts
export const BUILDER_LABEL = "builder:codex";
export type GhReads = {
  readonly labels: (issue: number) => readonly string[];
  readonly pullRequest: (branch: string) => PullRequest | null;
};
export const LIVE_GH: GhReads;
export const isRunning = (run: RunRecord | null): boolean;
export const snapshotOf = (issue: number, root: string, gh: GhReads): Snapshot;
```

`isRunning` is true when the run exists, its `ended` is null and its `pid` is alive (`process.kill(pid, 0)` returns, or throws with code `EPERM`).

- `LIVE_GH.labels` runs `gh api repos/ahl-gram/Vellum/issues/<issue> --jq '[.labels[].name]'` and parses the array; `LIVE_GH.pullRequest` runs `gh pr list --repo ahl-gram/Vellum --head <branch> --state all --json number,state --limit 1` and returns its first entry or null. Both through `execFileSync` with `encoding: "utf8"`.
- `snapshotOf`: `folder = folderOf(root, issue)`, `state = readState(folder)`; `builder` is `"codex"` when a record exists (the label is not read then) or when `gh.labels(issue)` includes `BUILDER_LABEL`, else `"claude"`. `running` is `isRunning(lastRun(state))` (false with no record). `outcome` is `outcomeOf` of the last run's last-message file, null when that file is absent. When the tree exists: `branch` from `git branch --show-current` run in it (empty prints null), `treeHead` from `git rev-parse HEAD`, and, with a branch, `remoteHead` from the first field of `git ls-remote origin refs/heads/<branch>` (empty prints null); with no tree, all three are null. `proverReported` is `existsSync(join(folder, FILES.proverReport))`. `pr` is `gh.pullRequest(branch)` with a branch, else null.
