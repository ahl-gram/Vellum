## The design, and what was rejected

### How the hook knows it is inside a headless build

The wrapper sets the environment variable `VELLUM_HEADLESS_BUILD` to the issue number on every `codex exec` and `codex exec resume` it starts. Codex hands its own environment to the hook process: measured by this planner (`out/1409-dry-run/notes.md` in the planner's tree, runs A and B, at `c435586c`): with the variable set on the `codex` process, the hook saw `marker: "from-codex-env"`; on a resume of the same thread launched without it, `marker: null`. Only `runCodexHook`, the Codex adapter's entry, reads it, and passes it into the request as `headlessBuild`; the engine, the checks and the Claude adapter never read the environment for it. The model's own shell sees the variable too (run A printed it), which is why no test helper and no shared module may read it: a headless build running `npm test` would otherwise judge the hook's own fixture rows as a build.

Rejected:
- **The payload's `permission_mode`**, which read `bypassPermissions` in run A. What an interactive session started with `-a never` reports was never measured, so it cannot be shown to mark headless builds alone.
- **Reading `source: "exec"` from the session file the payload's `transcript_path` names**: an undocumented file read on every call, and it would also mark every hand-started `codex exec` probe.
- **Refusing in every Codex session**: ruling 3 scopes the refusal to a headless build, and an interactive Codex session keeps its own flow.
- **A second entry in `.codex/hooks.json`, or a second launcher**: that file is frozen, pinned byte for byte by `test/repo/codex-hook.test.ts`, and any change to it drops Alex's trust until he re-trusts it in `/hooks`. The refusal lives in the launcher's code, which the frozen command already runs, so nothing needs re-trusting.

### What keeps a headless build from pushing, in two layers

**Layer 1: no login in the build's environment** (Alex's ruling, part a). How git and gh find a login on this Mac, read without printing a secret (`out/1409-dry-run/notes.md`, G):
- git's only credential helper is `osxkeychain`, set at system scope in `/opt/homebrew/etc/gitconfig`; the global scope holds only the commit identity, and `origin` is `https://github.com/ahl-gram/Vellum.git`;
- gh's login is `ahl-gram (keyring)`, and `~/.config/gh/hosts.yml` holds no token;
- `GH_TOKEN` and `GITHUB_TOKEN` are unset; `SSH_AUTH_SOCK` is set, but the agent holds no identity and `~/.ssh` no key file.

So `buildEnv` removes `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GIT_ASKPASS`, `SSH_ASKPASS`, `SSH_AUTH_SOCK`, `GIT_CONFIG_PARAMETERS` and every inherited `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`. It then sets:
- `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=credential.helper` and `GIT_CONFIG_VALUE_0=` (empty). An empty helper at the command scope empties git's helper list from every lower scope.
- `GIT_TERMINAL_PROMPT=0`, so a missing login fails rather than waits.
- `GH_CONFIG_DIR`, set to an empty folder in the record's folder.

Measured (G: dry runs only; H: inside a real headless Codex build, where Codex passed every one of these variables to the model's shell, `GIT_CONFIG_KEY_0` included):
- `git push --dry-run` exits 128 ("could not read Username ... terminal prompts disabled");
- `gh api user`, a public `gh api` read and `gh auth status` all exit 4 or 1 ("gh auth login");
- `git fetch`, `git ls-remote` (the repository is public) and the commit identity work as before.

Nothing the build needs breaks except `gh`, and the build needs `gh` only to read the issue, which the wrapper now does for it. `git -c credential.helper=osxkeychain push --dry-run` exits 0 with the environment stripped, which is why layer 2 refuses every `git -c`.

**Layer 2: the hook** (Alex's ruling, part b). In a headless build, before every other refusal, each segment the existing segmenter cuts (quotes and heredoc bodies blanked, separators split, the `env`, `command`, `time`, `exec`, `sudo`, `nohup`, `nice`, `builtin` and assignment prefixes stripped) is read word by word. Each word is trimmed of quotes, backticks, brackets and semicolons at its ends, and is compared by its last path part. The segment is refused when:
- it begins with a quoted command word (`"git" push`, `'git' push`, which the segmenter blanks to `""`);
- its first word is `eval`, `source` or `.`;
- any word is a shell: `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `csh` or `tcsh`;
- any word is `gh`;
- any word is `git` and, reading on from it as `gitCall` reads git, its global options carry `-c` or `--config-env`, or its subcommand is `push`, starts with `credential`, or is `config` with none of `--get`, `--get-all`, `--get-regexp`, `--get-urlmatch`, `--list`, `-l`, `get` or `list` after it;
- any word is `security` and the next one is `find-internet-password`, `find-generic-password`, `dump-keychain` or `export`;
- any word is `npm`, `npx`, `pnpm` or `yarn` and a later word is exactly `proof`; or any word, as typed, ends with `proof-runner/main.ts` and an earlier word is `node`, `npx`, `tsx`, `ts-node`, `bun`, `deno`, `pnpm` or `yarn`.

Measured in the planner's tree (`out/1409-dry-run/1409-r1-rule-probe.ts`, against `commandSegments` at `c435586c`): all 77 refused rows and 14 passed rows of T1 come out as T1 says.

**The hook sees the model's bare command, so refusing a shell does not refuse every command.** In run A the live payload's `tool_input.command` was `echo probe-1409-hook "marker=$VELLUM_PROBE_1409"` (`out/1409-dry-run/hook-dump.jsonl`), while the event stream shows Codex running it as `/bin/zsh -lc '<command>'`: that wrapper is Codex's and never reaches the hook. A shell word refuses only a shell the model typed itself.

**Unwrap and recheck, or refuse outright, form by form:**
- **Refused outright**: a shell, `eval`, `source` and `.`, a quoted command word, `git -c` and `--config-env`, a `git config` that writes, `git credential*`, a keychain read, and every `gh` call. Their payload is quoted text the segmenter blanks, or a setting that changes what a later command means, so no recheck could read it; and a headless build needs none of them, since Codex already runs every command in a shell.
- **Rechecked in place**, by reading every word rather than the command word alone: `xargs`, `env` with options (`env -u GIT_CONFIG_COUNT git push`), `timeout`, `nice -n`, a command called by its path (`/usr/bin/git push`), and a command in backticks or `$( )`. Their payload is plain words the read sees.

**`gh` is refused whole, which settles the `-X GET` question.** The ruling names `gh api` calls that send data fields under `-X GET`. The build has no gh login (layer 1), so no `gh` call can do it any good, a read included, and refusing all of it removes the read list and its `-X GET -f` hole together.

**The read errs toward refusing**, visibly and one edit away: `which gh`, `ls ~/.config/gh`, `echo git push`, `git config user.name` without `--get`, any `git -c`, any shell. The refusal's reason tells the build to run the command bare.

Rejected:
- **Unwrapping `bash -c '...'` and `eval '...'` to recheck their script**: the script is quoted text, so a recheck needs a second shell parser, and a spelling it misses (`bash -c "g""it push"`, `$'git\x20push'`) passes.
- **A read list for `gh` that refuses data fields whatever the method**, the ruling's literal form: it needs a gh login the build no longer has.
- **Refusing one-line programs** (`node -e`, `python3 -c`, `perl -e`): the build uses `node -e` and `perl -pi -e` for ordinary work, and with no login such a program cannot push either. Named as a miss.
- **Refusing edits to the hook's own files in a headless build**: it would stop Codex building any issue that changes the hook, and a build that edits its hook to push still finds no login. Named as a miss.
- **`GIT_CONFIG_NOSYSTEM` or `GIT_CONFIG_GLOBAL`**: dropping a whole config scope drops what is not a credential too. The helper reset at the command scope takes out only the helper, whatever scope sets it.
- **A network-off sandbox, or a separate macOS user**: declined by Alex (comment 7043367398).

### Who builds the tree, and who is the implementer inside the build

The wrapper builds the tree `.claude/worktrees/codex-<issue>` in the main checkout, as workflow step 7 builds one for a session with no isolation (fetch, `worktree add --detach ... origin/main`, the `node_modules` link), by `createPlan` from `scripts/agent-sandbox.ts`, so no copy of that recipe is written. The Codex implementer's own definition already expects this: its `implementer-tree` slot in `handbook/agents/adapters/codex-local.md` says the dispatcher made the tree and names it in the prompt, and its `implementer-branch` slot has it run `git switch -c` itself.

Inside the build, the `codex exec` session itself is the implementer: its prompt tells it to read `.codex/agents/vellum-implementer.toml` and follow it, with headless overrides. Issue #1400 was built the same way, by a Codex main session. The model and the effort are the role's from `.agents/model-policy.json`, passed on every run as `-m <model>` and `-c model_reasoning_effort="<effort>"` (Alex, 2026-11-20). Run C measured `-m gpt-6.2-sol` working headless, and runs E and F that the effort override takes on a build and, restated, on a resume (the session file recorded `medium`, then `low`, against the user default `high`).

Rejected: **the exec session spawning the `vellum-implementer` role** by name. Unmeasured headless; a resume by thread id would reach the parent and not the role; and the role's commands may not appear in the parent's `--json` stream, which is what Alex follows.

### What the build is told, and how it ends

The prompt (`scripts/handoff/prompt.ts`, its text under Files below) carries the plan, the tree, the session the trailers name, and the overrides the role body does not know:
- commit only;
- read the issue from the record's folder, since the build has no GitHub login;
- run each command bare;
- write what would be posted into the record's folder (`record.md`, `pr-body.md`, `guards.md`);
- stop where the definition would dispatch the guard prover or the plate reader, or open the pull request, whichever comes first;
- end the last message with exactly `OUTCOME: ready` or `OUTCOME: handback`.

Its first command is a hook check: `git push --dry-run origin HEAD:refs/heads/handoff-hook-check`, which the hook must refuse.
- That stands in for `CLAUDE.md`'s `/hooks` check, which a headless run cannot make, and it proves exactly the refusal this issue adds.
- Where the hook is not live, the dry run runs and fails for want of a login. So the prompt says only a refusal by vellum-footguns passes the check.

Rejected: **changing the implementer's role body** to carry the headless overrides. It would make this pull request change two generated agent definitions (workflow step 14's disclosure, a regeneration), for text only a headless build needs and that the wrapper's prompt already carries.

### The build's record

Everything for one build sits in `out/<issue>-handoff/` in the main checkout:
- `state.json`, the record the wrapper keeps;
- `run-<n>.jsonl`, the `--json` stream, which Alex follows with `tail -f`;
- `run-<n>.stderr.txt`;
- `run-<n>-last.md`, the last message;
- `issue.json` and `comments.jsonl`, the issue and its comments, which the wrapper writes, with Alex's own gh login, before every run;
- `gh-empty/`, the empty folder the build's `GH_CONFIG_DIR` names;
- the files the build and the session write: `record.md`, `pr-body.md`, `guards.md`, `prover-report.md`, `implementer-proof.md`.

Delivery folders already live in the main checkout's `out/`, and so does Codex's scratchpad.

### `next`, step by step

`next` gathers a snapshot (the label, the record, whether the last run's wrapper is alive, the last run's outcome line, the tree's branch and head, the branch's pushed head, whether `prover-report.md` exists, the pull request) and a pure function picks the step:

1. no record, no label: `claude-builds`;
2. no record, labelled: `plan`;
3. the last run has no end and its wrapper process is alive: `running`;
4. the last run handed back: `replan`;
5. the last run has no outcome line (or its wrapper died): `stopped`;
6. ready, but the tree is on no branch: `stopped`;
7. the pull request is merged: `retire`; closed unmerged: `closed`;
8. the tree's head is not the pushed head: `push`;
9. the pull request is open: `review`;
10. no prover report yet: `prove`;
11. otherwise: `open-pr`.

```ts
const SHELLS = new Set(["sh", "bash", "zsh", "dash", "ksh", "fish", "csh", "tcsh"]);
const PACKAGE_RUNNERS = new Set(["npm", "npx", "pnpm", "yarn"]);
const SCRIPT_RUNNERS = new Set(["node", "npx", "tsx", "ts-node", "bun", "deno", "pnpm", "yarn"]);
const KEYCHAIN_READS = new Set(["find-internet-password", "find-generic-password", "dump-keychain", "export"]);
const CONFIG_READS = new Set(["--get", "--get-all", "--get-regexp", "--get-urlmatch", "--list", "-l", "get", "list"]);
const FIRST_WORDS = new Set(["eval", "source", "."]);
const TRIM = /^[`'"(){};]+|[`'"(){};]+$/g;

const gitRefused = (raw: readonly string[], at: number): boolean => {
  let i = at + 1;
  while (i < raw.length && (raw[i] ?? "").startsWith("-")) {
    const option = raw[i] ?? "";
    if (option === "-c" || option.startsWith("--config-env")) return true;
    i += GIT_GLOBAL_WITH_VALUE.has(option) ? 2 : 1;
  }
  const sub = raw[i] ?? "";
  if (sub === "push" || sub.startsWith("credential")) return true;
  return sub === "config" && !raw.slice(i + 1).some((w) => CONFIG_READS.has(w));
};

export const headlessRefusal = (segment: string): string | null => {
  const raw = segment.split(" ").map((t) => t.replace(TRIM, ""));
  const words = raw.map((t) => t.split("/").at(-1) ?? "");
  const refused =
    segment.startsWith('""') ||
    FIRST_WORDS.has(words[0] ?? "") ||
    words.some(
      (w, i) =>
        w === "gh" ||
        SHELLS.has(w) ||
        (w === "git" && gitRefused(raw, i)) ||
        (w === "security" && KEYCHAIN_READS.has(words[i + 1] ?? "")) ||
        (PACKAGE_RUNNERS.has(w) && words.slice(i + 1).includes("proof")) ||
        ((raw[i] ?? "").endsWith("proof-runner/main.ts") && words.slice(0, i).some((x) => SCRIPT_RUNNERS.has(x))),
    );
  return refused ? HEADLESS_REASON : null;
};
```

- `CREDENTIAL_VARS` is `["GH_TOKEN", "GITHUB_TOKEN", "GH_ENTERPRISE_TOKEN", "GITHUB_ENTERPRISE_TOKEN", "GIT_ASKPASS", "SSH_ASKPASS", "SSH_AUTH_SOCK", "GIT_CONFIG_PARAMETERS"]`. `buildEnv` copies `base` without those names and without `GIT_CONFIG_COUNT` or any `GIT_CONFIG_KEY_<n>` or `GIT_CONFIG_VALUE_<n>`, then sets `VELLUM_HEADLESS_BUILD` to `String(issue)`, `GIT_CONFIG_COUNT` to `"1"`, `GIT_CONFIG_KEY_0` to `"credential.helper"`, `GIT_CONFIG_VALUE_0` to `""`, `GIT_TERMINAL_PROMPT` to `"0"` and `GH_CONFIG_DIR` to `ghConfigDir` (layer 1, The design).
- `runCodex` spawns `codex` with `stdio: ["ignore", <stream opened "w">, <stderr opened "w">]`, `cwd: io.cwd` and `env: io.env`, and resolves with the exit code; 127 when the process cannot start (its message written to the stderr file), 1 when it ends on a signal. - `outcomeOf` reads the last non-empty line, trimmed; `ready` for exactly `OUTCOME: ready`, `handback` for exactly `OUTCOME: handback`, null for anything else, an empty text included.
