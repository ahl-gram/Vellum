## 3. The design

`CLAUDE.md` stays the one instructions file both harnesses read (`AGENTS.md` stays a link to it). Its text becomes neutral where both harnesses can follow it. The steps only Claude Code can take move, word for word, to a new file Claude Code loads by itself, `.claude/rules/claude-code.md`. A short `## Codex` section, placed right after "What is tracked, and who this file assumes", tells a Codex session how to read the rest; it points at the existing homes rather than restating them: the menu rule at workflow step 6, the worktree recipe at workflow step 7, the shared Codex facts at the appendix of `handbook/agents/adapters/codex-local.md`, and the cross-harness hand-off at a new orchestration section. Rulings R1 and R9 become spec text: the planner, the designer and every review agent run from Claude Code whichever harness builds, and the epic plan's section 3.2 hand-off becomes `handbook/specs/orchestration.md`'s "Lanes that cross harnesses". `handbook/specs/conventions.md` gains the routing rule for main-session text by harness. A new unit test holds `CLAUDE.md`, read through the link, under the ruled byte budget, summed over every `AGENTS.md` on a launch folder's path, since Codex's limit is combined.

### Alternatives rejected

- **A real `AGENTS.md` generated from `CLAUDE.md` plus Codex text**: the issue keeps the link "unchanged in direction", and the render shows the link loads; a copy would need a drift check for no gain.
- **`AGENTS.override.md` or a nested `AGENTS.md` for Codex-only text**: Codex loads one file per folder and an override replaces `AGENTS.md` (Sub 1, X-21), and a nested file loads only for a session started at or below it.
- **A project `.codex/config.toml` setting that names an instructions file**: epic plan section 6 creates that file only for a ruled setting, Codex ignores project config in an untrusted project, and it would add a third home.
- **Moving the auto-memory paragraph to the rules file**: `test/repo/memory-pointers.test.ts` exempts `CLAUDE.md` by ruling A of Issue #729 and nothing else; the paragraph stays, and the Codex section names the memory as Claude Code's.
- **A guard that refuses any `AGENTS.md` but the root**: that is a policy Alex never ruled; summing per launch path encodes the measured rule without one.
- **A harness slot for the guard prover's fence pointer**: R4 says repoint; the sentence is true under both harnesses.
- **The Codex section restating the appendix's facts (the scratchpad, the shell folder, the patch tool, spawning cold)**: two homes for one rule (`handbook/specs/conventions.md`, exactly one home is normative).
- **Counting characters**: measured, Codex cuts by bytes.
- **The measuring helpers in `scripts/` or `test-support/`**: only this test uses them, and `test/repo/skill-links.test.ts` keeps its helpers in its own file (the Sub 5 precedent).

# Claude Code

Claude Code loads this file beside `CLAUDE.md` when a session starts, and Codex never reads it. It
holds the steps of `CLAUDE.md`'s sections that only Claude Code can take, each under the name of

## Process

- **Every definition under `.claude/agents/` carries an `effort`**, because an agent without one
  inherits the session's level. The check is `echo $CLAUDE_EFFORT` inside a dispatched agent, run
  from a session at some level other than that agent's own, since a session at the same level
  cannot tell the frontmatter from inheritance.

  conversation, and a cold review carries none of it (`handbook/specs/development-workflow.md`
  step 14).

## Worktrees

- **EnterWorktree is the normal way in.** It branches from `origin/main` rather than local HEAD, so
  the tree is current without a pull. One thing needs fixing by hand: any `/` in the name becomes `+`,
  in the branch AND the directory, and the branch takes a `worktree-` prefix on top. Rename the branch
  before the first commit, or the PR carries the harness's name instead of yours.
- **`vellum-planner` and `vellum-implementer` get their trees through `isolation: worktree`**
  in their frontmatter, so the harness builds and locks one at dispatch, a separate one for each. Inside such a tree, and inside any EnterWorktree tree,
  the harness is a fence: it refuses a compound command whose `cd` goes to a shell variable, any `git`
  run in a directory other than that worktree, a `for` loop around `git`, some quoted `jq` or `sed`
  constructs it cannot parse, and a call that names git (a `.git` path or the bare word `gitdir`
  included) once that call reads `$?`, while a plain single command passes (measured 2026-09-13 and
  2026-11-11, Issue #1340). A dispatched agent stands inside its dispatcher's fence, and its directory
  does not carry from one call to the next. That is why the sandbox recipes take `create`'s printed
  path literally, read the sandbox's sha from its `.git` file in calls of their own, and keep the `cd`
  in the call that runs. How a session runs several such lanes at once is
  `handbook/specs/orchestration.md`'s.
- **Do not switch worktrees while a dispatched agent is still running.** `EnterWorktree` and
  `ExitWorktree` in the parent silently disable that agent's commands for the rest of its life, and
  it goes on reporting what it can rather than failing, so the loss reaches you as a thin report and
  not as an error. Observed 2026-09-10: a cold skeptic finished its round with no tools left to it
