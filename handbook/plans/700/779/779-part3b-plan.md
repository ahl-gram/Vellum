## What the findings are, and their fixes

### `use-unknown-in-catch-callback-variable`

- **`e2e/run.ts`**: `.catch((e) => ...)` becomes `.catch((e: unknown) => ...)`. Its only read is `console.error("HARNESS ERROR:", e)`, which takes any value. The rulebook's skip list says the e2e tree carries no skip, so this line is fixed, not skipped.
- **That fix reds a unit test, found by recon.** The test "the runner actually uses the selection, the timings and the outcome rule it imports" in `test/repo/e2e-tiers.test.ts` finds the runner's error path by its spelling, `/\.catch\(\(e\) => \{([\s\S]*?)\n {2}\}\);/` over the runner's uncommented code, and asserts that path prints the tally. Every form the rule accepts changes that spelling, so the test is edited. The test searches source text, and the issue's ruling 2 and `handbook/specs/check-placement.md` say such a test moves out of source text as it is touched. **Menu item 2:**
  - **(a) edit the pattern in place**, replacing `(e)` with `(e: unknown)`: `/\.catch\(\(e: unknown\) => \{([\s\S]*?)\n {2}\}\);/`, one line, the assertion on the error path's body unchanged. This overrides ruling 2 for this one edit and leaves the test's move to this issue's part 2, the sorting pass, whose scope is every test that reads source as text. **Recommended**: part 2 sorts this test's eleven other spelling pins over the runner with it.
  - **(b) move the test's runner pins out of source text now**, as the spec says: a house lint rule over `e2e/run.ts` in `scripts/lint/`, with its own fixture test and its config block, holding what the twelve pins hold. Part 2's work, done here for one test; estimated at well over a hundred lines over four files, not built.
  - Considered and dropped: pulling the error path's tally into a named function that a unit test runs. It still searches source text for the call, as (a) does, and a whole-file pin for the call would pass with the call moved out of the error path, which today's pin catches (plan skeptic finding 2).
- **The seven `src/site` handlers**: each `.catch((err: Error) => ...)` becomes `(err: unknown)`. Six read `err.message` into a status line (`"The press jammed: " + err.message`); the Reading Room hands `err` to `rollBack(err: Readonly<Error>, wasArmed)`, which reads `err.message`, and `test/site/part-arguments.test.ts` holds that call's arguments to its parameters' names, so the call stays `rollBack(err, wasArmed)` and only the parameter's type changes. With `unknown`, each read needs narrowing. The rejection is an `Error` in practice (`runJob` in `src/site/explorer/worker-client.ts` rejects only with `Error`), but the handler also catches whatever its `.then` callback throws, so `unknown` is the honest type. A rejection that is not an `Error`, which no path produces today, would read as its own text in the status line rather than as "undefined".

The e2e runner keeps its own copy. **Recommended.**

### `no-confusing-void-expression`

- **`src/site/explorer/lod-controller.ts`**: `if (decision.action === "world") return revertToWorld();` inside `onSettle` becomes `if (decision.action === "world") { revertToWorld(); return; }`, the rule's own autofix. `revertToWorld` returns `void`, so `onSettle` returned `undefined` either way: no behavior change. `createLodController` already carries the rulebook's `max-lines-per-function` skip.
- **`test/site/table-drag-binder.test.ts`**: the four are one cause. `assert.deepEqual(d.revoked, [], "adopted, not revoked")` at line 100 is an assertion function (`asserts actual is T`), so it narrows `d.revoked` to `never[]` for the rest of the test, and each later `d.revoked.at(-1)` is typed `never`, which the rule reads as void. Asserting the length instead, `assert.equal(d.revoked.length, 0, "adopted, not revoked")`, is the same check and clears all four (`779c-voidfix.ts` at `5f8db4e`, the ruled options: lines 102, 104, 106 and 108 before, none after, no other rule and no fatal message).

### `no-useless-default-assignment`

- **The finding**: `buildLogPanel: (logPorts, presentYear, seed, subtitle, homecoming = null) => ...` in `barlessLogPanel` in `src/site/living-chart/no-bar.ts`; the rule says the default is useless "because the parameter is not optional".
- **The rule misreads this line, measured.** The arrow is typed from `VoyageLogPanel`, which is `ReturnType<typeof createVoyageLogPanel>`, whose `buildLogPanel` declares `homecoming: VoyageHomecoming | null = null`: the parameter IS optional, and `test/site/living-chart-no-bar.test.ts` calls the bar-less `buildLogPanel` with four arguments, so the default runs. The rule counts a parameter optional only when it is marked `?` or its type admits `undefined`, and a parameter made optional by a default in the signature it is typed from is neither (`779c-fp.ts`: a default under `typeof base`, where `base` defaults the parameter, is refused; the same default under `(a: number, b?: string | null) => string` passes).
- **At the installed version the rule's fix applies itself, and it can change what a program does with nothing going red.** In 8.70.0 the rule is `fixable: 'code'`, so `eslint --fix`, or an editor fixing on save, removes the default without asking. Where the value then reaches a slot that admits `undefined` (a template, `String()`, `??`, a truthiness read), the program's behavior changes and both the lint and the type check stay green: the plan skeptic ran `lintText` with `fix: true` on a `typeof base` default, `tsc --strict` passed the fixed text, and it printed `1:undefined` where it had printed `1:y`. No `--fix` is wired in `package.json`. Upstream made the fix a suggestion in v8.70.1 (PR #12826, "convert the fixer to a suggestion fixer", merged 2026-09-15, released 2026-09-21, read from `gh api repos/typescript-eslint/typescript-eslint/releases/tags/v8.70.1`), and 21 issues there name the rule.
- **Here, removing it is safe**: the value flows only into `buildVoyageLog` in `src/world/voyage-log.ts`, which itself declares `homecoming: VoyageHomecoming | null = null` and reads it by truthiness, so an omitted argument still arrives as "none".
- **The options, each measured on a scratch edit restored after (`npm run check`, `node --test test/site/living-chart-no-bar.test.ts test/site/reading-frame-log.test.ts`, `779c-measure.ts` with the rule):**
  - **(a) the rule's own fix**: remove `= null` in the stand-in. Check exit 0, 9 of 9 on the bar-less file, 0 findings.
  - **(b) make the parameter required where it is declared**: `buildLogPanel` in `src/site/living-chart/voyage-log-panel.ts` drops its `= null`, the stand-in drops its, and the one call that omits it (`test/site/living-chart-no-bar.test.ts`) passes `null`. Three lines in three files; check exit 0 (and exit 2 naming that call before it was given `null`), 15 of 15, 0 findings. The rule's report then becomes true, and the only production caller, `sessionLog` in `src/site/living-chart/voyage-session.ts`, already passes it.
  - **(c) say the parameter is optional where it is declared**: `homecoming?: VoyageHomecoming | null` in `voyage-log-panel.ts`; the stand-in keeps its default. One line; check exit 0, 15 of 15, 0 findings.
  - **(d) do not adopt the rule.** **Recommended**: its one finding in the tree is a misreport, its fix at the installed version can change behavior silently, and what it catches when right is a dead default, not a defect.
- **Menu item 3** is that choice.
