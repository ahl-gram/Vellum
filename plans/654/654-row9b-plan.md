Otherwise no new file.

**Four rules every split keeps** (9a's, with 9b's weight on the second):
- **Order is behaviour.** Claims, draws and emitted order stay in base order; a helper is called where its code ran.
- **No random draw is added, removed or reordered, on any stream.** This row's code draws on shared streams far more than 9a's: `simulateHistory` draws everything off one `rng` (and its four cyclers share it), `createNamer` keeps a per-namer used-set and an `overflow` counter across calls, `createLoreWriter` a per-writer used-map, `placeSettlements` one `site-jitter` draw per surviving candidate, `hamletCandidates` three draws then two sub-forks per lattice cell, `generateWorld` its namer's calls in a fixed order (settlement names, major rivers in index order, the two lakes, then sea, peak, forest and realms as the `names` literal evaluates them). A helper that draws is handed the rng, fork, cycler or namer the base drew from at that point and draws in the base order; where the base built an object literal whose fields draw (`{ year: yearAt(... rng.next() ...), text: rise() }`), the helper keeps the field order, since property evaluation order IS draw order. Fork creation order stays free (`fork` in `src/core/rng.ts` derives from seed and label).
- **A helper returns a new value and writes into nothing it was handed.** Where the base shares mutable state across phases, the state gets ONE owner: a module-level factory creates it and returns closures over it (the namer's used-set and overflow counter; the lore writer's used-map; `findLakes`' `seen` with its flood; `chainSegments`' `used` and start index), so a caller drives it through the owner's closures as the arena and the rngs are driven through their own methods. A per-call scratch buffer the base reused across iterations (`attachSeatlessLandmasses`' `queue` and `visited`) is allocated per call in its helper instead, the same bytes out at the same asymptotic cost (the base cleared it with `fill(0)` per landmass). Three writes through a parameter already stand at the base and are not re-homed onto new parameters: `wiring.roads.push` stays in `connectToNetwork`, `collect.push` stays in `findLakes`' flood, and `closeChainsOnBoundary`'s `pushCornersBetween(ring, ...)` becomes `cornersBetween(...)` returning the corners the caller appends, which removes one. The scratch syntax-tree scan (`654-9a-mutscan.ts`) is run at base and head and must report no NEW hit.
- **Every helper meets the size rules itself** (50 lines, depth 4).
- **Arithmetic moves verbatim** (plan skeptic 1): the same operands in the same grouping, and an accumulation rewritten as one expression keeps its left-to-right order. The byte sweep cannot see a regrouping where a value is only compared or rounded before anything is stored (the skeptic measured one in `connectToNetwork`'s step cost: 6,102 of 32,250 reuse-branch costs changed bitwise and 0 of 100 worlds moved), and neither can a control, since a one-ulp plant moves nothing. So a scratch syntax-tree comparison (`654-9b-arith.ts`) prints every arithmetic expression (`+ - * / % **`, compound assignments included) of each of the 21 files at base and head, types stripped, and lists the head expressions with no identical base expression and the base ones with no head match; every one is read, and one that is not a pure rename of an operand is a defect. It is proved first on the skeptic's regrouped `connectToNetwork` (`654-9b-skeptic-roads-assoc/`). The sites it guards by name, where only this check sees a regrouping: `roadSearch`, `realmStepCost`, `closeChainsOnBoundary`'s boundary positions and gaps, the `Math.round` projections in `projectSettlements`, `regionRoadLabels` and `regionSeaGate`, and the rounded history years (`yearAt`, the ruin year).
